# Habits — Telegram Mini App

Набор мини-приложений в одном Telegram WebApp: трекер привычек, чек-листы,
дневник, менеджер паролей, ссылки, конвертер валют.

- **Прод:** https://telegram.resager.ru/app/habits/
- **Стек:** Go (stdlib `net/http`, pgx) + PostgreSQL · Vue 3 + Vite + TypeScript
- **Отложенное:** `habits/BACKLOG.md` — разобранные, но не сделанные задачи
  (по страницам): что уже готово, что придётся переделать, какие решения
  нужны и оценка. DOCS описывает то, что есть; BACKLOG — то, что может быть.
- **Актуальный код:** бэкенд `habits/backend`, фронтенд `habits/frontend/app`,
  деплой `habits/deployment/streaks`. Каталоги `habits/bakend` и
  `habits/frontend/webapp` — предыдущее поколение, не используются.

## 1. Функционал

### Главная (`/`) — v2.80
- **Порядок страниц общий у меню и плиток** (v2.79): сверху закреплённые,
  дальше те, где у пользователя есть данные, внизу пустые; в меню группы
  разделены подписью «без данных». Смысл — ничего не прятать, но и не
  заставлять пролистывать два десятка страниц, в которые ни разу не заходили.
  Закрепление — кнопка 📌 у правого края пункта меню (лежит НАД пунктом:
  кнопка в кнопке — невалидная вёрстка), хранится на сервере
  (`user_settings.menu_pinned_pages`, миграция 0107), порядок закреплённых =
  порядок закрепления. Признак «есть данные» считает сервер
  (`GET /me/pages/order`): один запрос, по `EXISTS` на главную таблицу каждой
  страницы (`store/pageorder.go`, карта `pageDataSources`); страница без
  источника (Settings, Help, админские) всегда считается пустой. Карта
  грузится при старте, поэтому только что заведённые данные меняют порядок со
  следующего запуска. localStorage — кэш на первый кадр, иначе плитки
  успевают нарисоваться в исходном порядке и прыгают.
- **Скрытые страницы не показываются** ни в меню, ни на плитках (v2.80):
  список — `user_settings.hidden_pages`, настраивается в Settings → «Какие
  страницы мне видны». Фильтр стоит внутри `sortPages()`, а не у вызывающих:
  меню и главная зовут одну функцию, и забыть его в одном из мест нельзя.
- **Набор плиток = набор пунктов меню.** Раньше главная брала только `meta.app`,
  а меню добавляло admin-страницы, и они молча разошлись.
- **Блок плиток сворачивается** — `ui_collapsed`, ключ `main`, id 1 (не
  localStorage: в вебвью Telegram он периодически чистится).
- **Версия страницы** — `meta.version` в роутере, видна админу в меню; рядом с
  заголовком «Habits» там же показывается версия всего приложения.
  Заполняется РУКАМИ при заметной правке — это отдельный пункт в порядке
  релиза: вывести её из истории нельзя, релиз обычно трогает несколько страниц.
  У 11 страниц старше журнала изменений пусто, и это осознанно.
Стартовая страница-знакомство: плитки всех мини-приложений (показываются
только доступные пользователю — см. «Доступ к страницам»). Сверху —
**глобальный поиск** по данным всех своих страниц (кроме паролей — они не
покидают устройство): категории Tracker, чек-листы и шаблоны, записи дневника,
ссылки (имя/URL/теги), метрики, напоминания, серверы; результаты группируются
по страницам, клик ведёт на страницу. Под плитками — блок «🔔 Ближайшие
напоминания». Последняя открытая вкладка запоминается **по умолчанию**
(отдельной опции на главной больше нет).
Навигация — левое выезжающее меню (тоже фильтруется по доступам).

### 📊 Tracker (`/tracker`) — v2.81
Трекер привычек. Категории (имя + цвет), у каждой — сетка 8 недель × 7 дней
(недели с понедельника, сегодня подчёркнуто). Клик по клетке — отметка
(оптимистично, с откатом при ошибке). Категории сворачиваются шевроном —
состояние хранится на сервере (`user_settings.ui_collapsed`) и переживает
очистку webview. Календарь-модалка по месяцам с
навигацией и отметками. Настройки категории: переименование, цвет, удаление,
галочка **Daily** — помечает категорию как ежедневную привычку: в Reminders
для неё можно создать напоминание, которое приходит, только если день ещё
не отмечен.

**Виды трекеров** (настройки категории): *отметки* или *счётчик*. Счётчик —
в клетках числа, клик +1, долгое нажатие −1, ниже нуля не уходит (ноль =
отсутствие строки в БД). У отметок три **стиля**: квадратики, кружки, эмодзи.
Опция **мультицвет** (для квадратиков/кружков) и **мульти-эмодзи** (для
эмодзи): в разные даты можно ставить разные цвета/эмодзи — рядом с 📅
появляется иконка активного цвета/эмодзи, по клику пикер (палитра/набор +
последние использованные; активный выбор — в localStorage,
`tracker_active_v1`). Клик по отметке другого цвета/эмодзи перекрашивает её в
активный, того же — снимает.

**Набор именованных цветов** (v2.81, `tracker_categories.palette` JSONB,
миграция 0111): в настройках трекера — список «цвет + название», до 12 штук,
у цвета можно включить **градиент** (второй цвет). Названия видны ТОЛЬКО в
настройках: на отметках они не рисуются, это подпись для человека. Когда
набор непустой, на карточке вместо одного кружка идёт строка кружков всего
набора, и клик по кружку не открывает палитру, а выбирает активный цвет;
пустой набор — поведение как раньше (один кружок → палитра). Мультицвет при
непустом наборе включается принудительно (иначе все отметки были бы одного
цвета). Активным может быть только цвет из набора — иначе после удаления
цвета из набора отметки продолжали бы ставиться исчезнувшим цветом.
Значение цвета отметки (`tracker_marks.color`) — `#rrggbb` или пара
`#rrggbb,#rrggbb` для градиента: отметка хранит цвет целиком и не ссылается
на набор, поэтому правка набора не перекрашивает историю задним числом.
Строка цвета проверяется регуляркой перед подстановкой в `style` (`colorCss`
в `display.ts`) — непроверенное значение из БД в CSS пускать нельзя.

**«Последние использованные» в пикере** (исправлено в v2.81): список берётся
из реальных отметок трекера (свежие дни первыми) и только потом дополняется
списком с устройства. Раньше он состоял ТОЛЬКО из localStorage, который в
вебвью Telegram периодически чистится, — и вместо последних цветов человек
видел пустоту и общую палитру пресетов. У одноцветных трекеров цвет отметки в БД NULL —
смена цвета категории перекрашивает и старые отметки. **Вся история** (кнопка
в настройках) — полноэкранный вид всех отметок помесячно с самой старой
(свежие месяцы сверху, итог «отметок/сумма», клетки кликабельны).
**Совместный доступ**: владелец в настройках выдаёт доступ пользователю
приложения (точный id или @логин, получателю — уведомление от бота, подсказки
из общего списка получателей). Участники видят трекер у себя (бейдж 👥 у
названия), ставят отметки и могут создавать Daily-напоминания, но настройки,
шаринг и удаление — только у владельца; участник может покинуть трекер
(настройки → «Покинуть»), владелец — отозвать доступ (✕ у участника).

### ✅ Checker (`/checker`) — v2.83
Чек-листы: группы с пунктами. Отметка выполнения, добавление пунктов инлайн,
переименование/удаление группы, удаление пункта (подтверждение вторым тапом).
**Промежуточный статус «в работе»** (v2.82 — сама отметка, v2.83 — включение
на группе). Галочка **🚧 Промежуточный статус** в настройках ГРУППЫ
(`checker_groups.progress_mode`, миграция 0115); включена — клик по пункту
идёт по кругу **пусто → в работе → сделано → пусто**, то есть полная отметка
в два клика, выключена — один клик, как было. Опция на группе, а не на
пункте: «в работе» — свойство списка (ремонт, переезд), а не отдельной
строки, и отмечать режим каждому пункту руками пришлось бы столько раз,
сколько в списке пунктов.

Пункт в работе: акцентная рамка и наполовину закрашенный квадрат вместо
галочки (форма, а не только цвет — состояние читается и в темах с приглушённым
акцентом), название акцентным цветом. В полоске прогресса группы «в работе»
идёт приглушённым сегментом сразу за сделанным: иначе группа, где всё начато
и ничего не закончено, выглядит нетронутой.

Хранение — `checker_items.in_progress` (миграция 0113), отдельным флагом, а не
значением `done`: по `done` считаются прогресс, история и повторяющиеся
сбросы, и делать его тройственным значило бы переписать всё это. Отмеченный
пункт «в работе» быть не может — флаг снимают `done = true` (в том числе
массовое «отметить все») и повторяющийся сброс группы; на клиенте то же самое
делается сразу, до ответа сервера, иначе галочка и «в работе» на миг горят
вместе. При выключенном режиме группы флаг не поставить и запросом напрямую
(подзапрос к `progress_mode` в `UpdateCheckItem`), а выключение режима гасит
флаги пунктов группы — иначе осталось бы невидимое состояние, всплывающее при
повторном включении.

**Многострочное поле названия** (v2.82): в окне пункта название правится в
`textarea`, которая растёт под текст (`shared/autoGrow.ts`, общий хелпер — он
же у поля нового пункта и у заметки). Пункты бывают на две-три строки, и в
однострочном `input` правился видимый кусок вслепую. Enter в поле ставит
перенос строки, сохранение — кнопкой или Ctrl/⌘+Enter. У высоты есть потолок
(320px): без него длинная заметка выталкивала кнопки «Сохранить» и «Удалить»
за экран.

**Окно пункта** (v2.22 — по долгому нажатию; v2.35 — ещё и по видимой кнопке
**✏️** на пункте): правка названия, **заметка/описание** (`note` на
`checker_items`, ≤4000 символов, показывается под названием пункта), **метку**
(эмодзи-маркер приоритет/цвет/эмодзи, `label` ≤16, v2.38 — пресеты 🔴🟠🟡🟢🔵⭐🔥❗📌
или своё, показывается перед названием), **выбор
группы для переноса пункта** (v2.34 — `group_id` в `PATCH /checker/items/{id}` →
`MoveCheckItem`, список групп полным путём «Родитель › Подгруппа») + «Сохранить»/
«Удалить»; тап при этом не переключает галочку.
**Прогресс-бар** у заголовка группы (v2.35): полоска по прямым пунктам рядом со
счётчиком «сделано/всего»; если есть подгруппы — ещё «Σ done/total» по всему
поддереву. **Массовые действия** в настройках группы (⚙️): «отметить все» /
«снять все» / «удалить выполненные» (`POST /checker/groups/{id}/items/bulk`). Группы сворачиваются,
состояние на сервере, как у Tracker. Счётчик «сделано/всего» у заголовка группы
показывается **всегда** (v2.33, раньше — только в свёрнутом виде; считает прямые
пункты группы). В настройках группы (⚙️) — чекбокс **«Скрывать выполненное»**
(`hide_done` на `checker_groups`): выполненные пункты не показываются в списке, но
учитываются в счётчике.
**Подгруппы (v2.21, вложенность любой глубины — v2.32)** — из настроек любой
группы/подгруппы (⚙️) можно добавить подгруппу; она рендерится вложенной
карточкой (рекурсивный `CheckGroupCard`, `parent_id`). У подгрупп **нет
собственной подложки** — только левая линия-акцент и отступ, фон
родителя-карточки (в т.ч. «стекло») просвечивает. Удаление родителя каскадно
уносит всё поддерево (Postgres `ON DELETE CASCADE`, любая глубина). **Предел
вложенности — 20 уровней** (`store.MaxCheckerDepth`, группа верхнего уровня =
1-й), единый для ручного создания (`CreateCheckGroup` считает глубину родителя
рекурсивным CTE → `ErrTooDeep` → 409 `too_deep`), импорта и раскрытия в Projects;
в UI кнопка «➕ Подгруппа» скрывается на 20-м уровне с подсказкой.
**Структурные операции (v2.36)**: **смена родителя** группы через select в
настройках (`POST /checker/groups/{id}/move` → `MoveCheckGroup` с проверкой цикла —
нельзя вложить в своё поддерево, 409 `conflict` — и предела глубины: глубина нового
родителя + высота поддерева ≤ 20); **перестановка перетаскиванием** за заголовок
среди соседей (pointer-события, `useGroupReorder`, живая сортировка мутацией
`position` → `POST /checker/groups/reorder`); **дублирование** группы со всем
поддеревом, сохраняя отметки и заметки (`POST /checker/groups/{id}/duplicate` →
`DuplicateCheckGroup`, имя «<name> (копия)»).
**Совместный доступ (v2.40)** — в попапе «Поделиться» блок «👥 Совместный доступ»: владелец открывает доступ к списку верхнего уровня участнику (по id/@логину, `POST /checker/groups/{id}/share-access`, kind `checker_share` — доступ, не копия). Участник видит общий список (бейдж 👥 + имя владельца) и **меняет пункты** (отметить/добавить/править/удалить/массовые) — проверка `checkerAccess` (владелец корня или участник) на всех операциях с пунктами; структура (переименование, подгруппы, перенос, порядок, удаление, шаринг) — только владелец. `ListCheckGroups` возвращает свои + расшаренные поддеревья с `mine/shared/owner_name`. Участник может «Покинуть список» (`DELETE /checker/shared/{id}`), владелец — управлять участниками (`GET .../shares`, `DELETE .../shares/{userID}`). Бейдж 👥 у общих списков — как в Tracker/Tasks. **История изменений (v2.41)**: в настройках списка кнопка «🕘 История» показывает, кто что сделал (добавил/отметил/снял/удалил/перенёс пункт, массовые действия) — `checker_history` на корень списка, `GET /checker/groups/{id}/history`, видна владельцу и участникам.
**Дедлайны/напоминания (v2.43)** — у пункта (в окне пункта) или у списка (в
настройках) можно задать момент напоминания; бот в срок пишет владельцу и
участникам («⏰ Напоминание: «пункт» в списке «X»»). Колонки `remind_at`/
`reminded_at` на `checker_items` и `checker_groups`; воркер `internal/checkerreset`
(тот же тик) шлёт наступившие (пункт — только если не выполнен) и помечает
`reminded_at`. Эндпоинты `POST /checker/items/{id}/reminder`,
`POST /checker/groups/{id}/reminder` ({remind_at|null}). Маркер ⏰ у пунктов с напоминанием.
**Повторяющиеся списки (v2.42)** — у списка верхнего уровня расписание сброса
(none/daily/weekly/monthly + время + день недели/месяца + смещение TZ, колонки
`reset_*`/`next_reset_at` на `checker_groups`). Фоновой воркер `internal/checkerreset`
(тик 1 мин) по `next_reset_at` сохраняет **снимок дня** (`checker_snapshots`:
done/total + JSON-дерево) и снимает все отметки, затем считает следующий сброс
(`nextResetAt`, чистая функция, есть тест). Ручной сброс — `POST /checker/groups/{id}/reset`
(владелец/участник). Календарь-история (`GET .../snapshots`, `.../snapshots/{day}`):
насыщенность дня = доля выполненного, тап — просмотр чек-листа за день (read-only,
`HistoryCalendar`). Бейдж 🔁 у повторяющихся списков.
**Корзина / отмена удаления (v2.37)**: удаление группы — **мягкое**
(`deleted_at` на группе и всём поддереве; `SoftDeleteCheckGroup`), группа
исчезает из списка, но лежит в корзине. Сразу после удаления — баннер
«…в корзине · Отменить» (`POST /checker/groups/{id}/restore`). **Корзина**
(кнопка внизу страницы, `GET /checker/trash`): список удалённых корней с
агрегатами (групп/пунктов в поддереве, когда удалено), восстановление, удаление
навсегда (`DELETE /checker/trash/{id}` — каскад), очистка целиком
(`DELETE /checker/trash`) и **срок хранения** (`user_settings.checker_trash_days`,
1–365 дней, `PUT /checker/trash-days`). Просрочённое чистится **лениво** при
открытии Checker и корзины (`PurgeExpiredCheckerTrash`). Все чтения групп
(список, копирование, шаринг, раскрытие в Projects, смена родителя/порядок)
исключают `deleted_at IS NOT NULL`.
**Поиск (v2.32)** — глобальное поле поиска на странице фильтрует группы по имени
и пунктам (включая пункты подгрупп любой глубины); при активном поиске карточки
раскрываются, показываются только совпавшие пункты/ветки, а **совпавшие слова
подсвечиваются** (v2.33, `highlightParts` — сегменты `<span class="hit">`, без
v-html). У каждой группы с подгруппами есть свой 🔍 — локальный поиск по её
поддереву (`search.ts`: `groupRelevant`/`visibleItems`).
**Шаблоны** — многоразовые списки («сборы в поездку»): «запустить» разворачивает
шаблон в свежую группу с неотмеченными пунктами; любую группу можно сохранить
как шаблон из её настроек. **С подгруппами (v2.39)**: тело шаблона хранится
деревом (`checker_templates.body` JSONB, миграция 0038 перенесла плоские
`checker_template_items` в `body.items`); редактор принимает формат «- пункт /
# подгруппа» (как импорт), «сохранить как шаблон» кладёт всё поддерево, запуск
создаёт группу с подгруппами, шаринг/redeem сохраняют дерево. Шаблон можно удалить прямо из строки (🗑,
подтверждение вторым тапом) или из окна редактирования.
**Шаринг шаблона / группы**: 1) пользователю приложения по точному id или
@логину (получателю приходит уведомление от бота, копия добавляется ему);
2) **ссылка-приглашение** `t.me/<бот>?startapp=chk_<токен>` (шаблон) или
`startapp=chg_<токен>` (живая группа с подгруппами любой глубины, v2.21) — для любого друга в
Telegram: он открывает ссылку, Mini App запускается и автоматически добавляет
копию (повторное открытие не дублирует). Делиться группой можно из её настроек (⚙️).
**Экспорт/импорт группы (v2.23)** — из настроек группы (⚙️) «⬇️ Экспорт»
показывает группу простым текстом (первая строка — имя, пункты «- …», подгруппы
«# …», глубина = число «#»: «##» — подгруппа 2-го уровня и т.д.) и JSON
`{name, items:[{name,done}], subgroups:[…]}` (рекурсивные `subgroups`). Внизу
списка «⬆️ Импорт»: вставленный текст/JSON распознаётся автоматически
(`transfer.ts`), `POST /checker/groups/import` создаёт дерево любой глубины на
сервере. Текст простой — состояние галочек в нём опускается; JSON сохраняет `done`.
Чек-лист-ссылка в Projects раскрывается рекурсивно (`CheckerGroupView`).

### 🗂 Tasks (`/tasks`)
Задачи: разовые дела со сроками, приоритетами и жизненным циклом. Быстрое
добавление одной строкой (поле + выбор категории). **Категории** (в UI;
в API/БД исторически project) — группы задач (цвет + имя), сворачиваются
(`ui_collapsed`, app `tasks`, «Входящие» = id 0); задачи вне категории —
«Входящие». **Вкладки**: Сегодня (срок сегодня +
просроченные, просрочка красным, приоритет важнее), Планы (группы по датам,
«Просрочено» первой), Все (по категориям, ручной порядок стрелками ▲▼),
Выполненные (лог по дням, клик по кружку возвращает в работу).
**Статусы**: стандартные Открыта/Выполнена/Архив; в категории переопределяются
(до 20, у каждого имя + kind: open/done/archived — kind задаёт поведение:
done перечёркивает и уводит в лог, archived скрывает; нужен минимум один open
и один done). В карточке статус — выпадающий список, переключается в любом
порядке. **Карточка задачи**: статус, приоритет (полоска слева:
зелёный/оранжевый/красный), категория, срок (дата + опц. время), 🔔 напомнить
(за N минут), повторение (daily/weekly/monthly/интервал N дней — при
выполнении создаётся следующий экземпляр со сдвинутым сроком), исполнитель
(в общих категориях), подзадачи-чеклист (прогресс «2/5» на строке), описание
в Markdown (рендер как в Articles). **Настройки категории**: цвет, свои статусы,
параметры новых задач по умолчанию (приоритет, напоминание, повтор),
совместный доступ (по id/@логину, бейдж 👥; участники видят все задачи
категории, добавляют и выполняют их, настройки/удаление — у владельца; участник
может покинуть). **Уведомления ботом** (воркер, раз в минуту): «подходит
срок» в момент срока или за N минут (для задач без времени срок = 09:00
пользователя) и один раз «просрочена» (без времени — после конца дня);
получатель — исполнитель или автор. На главной — бейдж на плитке
(сегодня + просрочено, красный при просрочке) и секция в глобальном поиске.

### 📔 Diary (`/diary`)
Дневник: записи с датой-временем, редактирование, удаление, живой поиск
(debounce 300 мс, ILIKE на сервере), фильтр по диапазону дат.
Длинные записи (>400 символов или >6 строк) в списке укорачиваются
(line-clamp на 6 строк) и разворачиваются/сворачиваются кнопкой (v2.17).
Экспорт в .txt/.csv за период — в настройках страницы (шестерёнка в
шапке, генерация на клиенте).

### 🔑 Passwords (`/passwords`) — E2E-шифрование + синхронизация
Менеджер паролей. Шифрование **всегда на устройстве**: PBKDF2-SHA256
(310k итераций) → AES-256-GCM; мастер-пароль не покидает устройство.
**Синхронизация через сервер**: один зашифрованный блоб на пользователя
(`password_vaults`) с **версионированием** (optimistic-блокировка — PUT со
старой версией получает 409, клиент подтягивает серверную и предупреждает,
что изменение с «отставшего» устройства не применено). localStorage — кэш
на случай недоступности сервера: оффлайн-правки помечаются dirty и
досылаются; старые локальные хранилища мигрируют на сервер при первом входе.
На странице показывается **версия и время последнего дампа** на сервер.
- **Папки: вложенные** (дерево), **закрепляемые** 📌 (показываются первыми);
  при удалении содержимое переносится на уровень выше.
- **Передача папки пользователю** по id/@логину: поддерево с паролями
  шифруется на устройстве отправителя случайным ключом, получатель видит
  баннер «Принять/Отклонить» и получает уведомление от бота.
- Записи: **обязательно только название**; логин, пароль, **ссылка**
  (кнопка 🌐 перейти), описание, TOTP. **Поиск** по названию/логину/ссылке/
  описанию. **Порядок** меняется кнопками ⬆️⬇️ в редактировании.
- **Индикатор надёжности пароля**: полоска красный → оранжевый → жёлтый →
  зелёный (оценка по энтропии), работает и для мастер-пароля при создании.
- **Генератор паролей**: длина 8–64, наборы символов, crypto.getRandomValues
  без modulo bias, минимум по одному символу из каждого набора.
- **TOTP (2FA)**: base32-секрет или otpauth:// URL — живой 6-значный код
  (RFC 6238) с отсчётом, тап — копирование.
- **Автоблокировка по бездействию** — опциональная (выкл/1/5/15 мин).
Экспорт/импорт в настройках страницы (шестерёнка): файл **опционально
шифруется** (AES-256-GCM,
пароль файла может отличаться от мастер-пароля); импорт понимает
зашифрованный и открытый формат, заменяет хранилище по подтверждению.

### 🔗 Links (`/links`)
Менеджер ссылок: папки с произвольной вложенностью, ссылки с тегами,
избранное ⭐, топ-10 📈 по количеству переходов, поиск по названию/URL/тегам,
подсказки тегов, «вставить из буфера», экспорт папки/всего дерева в JSON,
импорт JSON и списком URL (с выбором папки, общими тегами и «умными» тегами по
домену).
**«Поделиться» — попап как в Checker** (у папки и у отдельной ссылки, кнопка
📤): три способа в одном экране —
- *Пользователю приложения* (по id/@логину) — получатель получает **копию**
  (папка → всё поддерево, ссылка → сама ссылка в корень) через общий
  `deliverShare` (`POST /links/folders/{id}/share` kind `links_folder`,
  `POST /links/{id}/share` kind `link`): сразу при auto_accept, иначе во
  «Входящие» на Contacts;
- *Ссылка-приглашение* `t.me/<bot>?startapp=lnf_<token>` (папка) /
  `lnk_<token>` (ссылка) — друг открывает её и получает копию (redeem-эндпоинты
  `/links/folders/redeem`, `/links/redeem`; токен на объекте, `share_token`);
- *Копировать текстом* — прежнее поведение (папка → список ссылок текстом,
  ссылка → её URL).
Отправка по id и ссылка-приглашение работают только с **серверным** хранилищем
(у объекта должен быть серверный id); копирование текстом — всегда.
**Хранилище на выбор** (настройки страницы, шестерёнка): локально
(localStorage) или на сервере;
кнопка переноса данных между хранилищами. Сам выбор хранится **на сервере**
(`user_settings.links_storage`): Telegram-webview периодически очищает
localStorage, из-за чего настройка «слетала» на локальное хранилище.
Кнопка «вставить из буфера» работает каскадом: Clipboard API → Telegram
`readTextFromClipboard` → поле ручной вставки (долгое нажатие → «Вставить»).
**Проверка битых ссылок** (опция `links.dead_check`, выдаётся админом
персонально): воркер раз в час обходит ссылки (повторная проверка каждой —
раз в 12 ч, HEAD с фолбэком на GET), мёртвые помечаются 💀 в списке;
401/403/429 живыми считаются, смена URL сбрасывает пометку.

### 📈 Metrics (`/metrics`)
Произвольные метрики: категории («Здоровье»), внутри — элементы-графики
(«Вес», «Сон», «SpO2»). Точка добавляется на текущее время по умолчанию,
можно задать любую дату (в т.ч. в прошлое — встанет в середину графика).
Под графиком — список точек (клик — редактирование/удаление).
Категории и элементы сворачиваются (состояние — локально).
**Типы графиков хранятся на бэкенде отдельной сущностью**
(`metrics_chart_types`: line/bars/tubes; новые типы — новой строкой):
- *Линейный*: несколько серий разными цветами, цвет узлов отдельно от линии,
  градиент-заливка под линией.
- *Столбики*: настраиваемые цвета/ширина/зазор; мультикомпонентные точки
  рисуются сегментами (первый компонент — весь столбец, остальные снизу
  вверх — например сон: всего/глубокий/быстрый).
- *Трубки* (MiFit-style): тонкие вертикальные трубки, внутри окрашенный
  сегмент диапазона min–max (например SpO2).
Фон графика: без цвета — прозрачный, можно цвет или градиент.
Конфигурация элемента — JSONB (`config`): компоненты (ключ/название/цвет)
и настройки типа.

### 🔔 Reminders (`/reminders`)
Напоминания, которые приходят **сообщением от бота** в Telegram (тем же ботом,
что открывает Mini App; пользователь должен хотя бы раз запустить бота).
Типы (kind):
- *once* — один раз в указанные дату и время;
- *daily* — каждый день в заданное время;
- *weekly* — по выбранным дням недели (чипы Пн–Вс, битовая маска);
- *monthly* — в число месяца (если в месяце нет 31-го — последний день);
- *yearly* (v2.17) — ежегодно в дату (день + месяц + время) — для праздников
  и дней рождений; 29 февраля в невисокосный год сдвигается на 28-е;
- *interval* — каждые N минут/часов/дней/недель/месяцев (единица выбирается
  в форме, хранится в минутах, месяц = 30 дней; минимум 5 минут, максимум год);
- *tracker* — триггер по привычке из Tracker: приходит в заданное время
  **только если категория ещё не отмечена за сегодня** (день считается в
  таймзоне пользователя); в выборе категорий daily-помеченные показаны первыми.
Каждое напоминание можно выключить/включить тумблером (без удаления),
у включённых видно следующее срабатывание («сегодня 21:00», «завтра 09:00»).
**Свои категории** (v2.17, `reminder_categories` + `reminders.group_id`):
напоминания раскладываются по сворачивающимся группам («Без категории» —
отдельная группа; сворачивание хранится на сервере, app='reminders');
удаление категории не трогает напоминания (FK SET NULL). Кнопка вверху
переключает **компактный режим** списка (localStorage).
**Экспорт/импорт/шаринг категории (v2.23)** — из настроек категории (⚙️):
«⬇️ Экспорт» (читаемая сводка + JSON `{name, reminders:[…]}`), «📤 Поделиться»
(пользователю приложения или ссылка-приглашение `startapp=rem_<токен>`). Внизу
списка «⬆️ Импорт категории (JSON)» → `POST /reminder-categories/import`.
Копирование/импорт переносит напоминания с пересчётом `next_fire_at`, **кроме
kind=tracker** (завязаны на привычки Tracker получателя). `share_token` —
столбец `reminder_categories`.
Время задаётся в локальной таймзоне пользователя (`tz_offset_minutes`
сохраняется с напоминанием, сервер пересчитывает в UTC).
Фоновый воркер (`internal/reminders`) раз в 30 с выбирает наступившие
(`next_fire_at <= now`), шлёт `sendMessage` через Bot API и планирует
следующее срабатывание; once после отправки выключается. Ошибка отправки
(бот не запущен/заблокирован) не блокирует перенос.

### 💱 Converter (`/converter`) — v2.78
- **Справочник валют** (`GET /converter/available`): весь список источника,
  фиат и крипто. Источник не помечает, где что, — зашит список ISO 4217, всё
  остальное показывается как криптовалюта (ошибка безобидна: это лишь
  группировка в выборе).
- **История курсов** — таблица `currency_history` (миграция 0104). Всё хранится
  **относительно доллара** (сколько единиц за 1 USD): любая пара получается
  делением, матрица «каждая к каждой» не нужна. День — `DATE`: источник отдаёт
  дневные срезы.
- ⚠️ **Недостающие дни докачиваются по требованию** — источник держит
  датированные срезы, иначе первый график пришлось бы ждать месяц. Ошибки
  докачки молчаливые: пропуск дня — дырка в графике, а не пустой экран.
  Потолок периода 92 дня: каждый день это отдельный запрос к источнику.
  День считается собранным, только если в нём есть ВСЕ запрошенные валюты.
- **График — свой компонент, не общий Sparkline**: тот считает ось от нуля, и
  курс, весь месяц державшийся около 385, был бы прямой линией у края. Здесь
  масштаб от минимума до максимума с запасом 10%.
Конвертер валют: базовая валюта + список валют пользователя (хранится на
сервере). Ввод в любую строку пересчитывает остальные. Курсы —
`@fawazahmed0/currency-api` через jsDelivr CDN (бесплатно, без ключа,
поддерживает и криптовалюты), кэш на бэкенде **1 час** на пару base:target.

### 📄 Articles (`/articles`)
Текстовые статьи с **Markdown-разметкой** (GFM, как README на GitHub:
заголовки, таблицы, код, цитаты, списки задач; рендер — marked + DOMPurify).
**Вложенные категории** как в Links. Клик по статье открывает её **на весь
экран** (заголовок сверху, крестик закрыть); ссылки из статьи открываются
через Telegram. У каждой статьи меню ⋮: *изменить* (редактор с
markdown-текстом и выбором категории), *скачать* (.md на устройство),
*поделиться*. Шаринг тремя способами: пользователю приложения по id/@логину
(копия + уведомление от бота), ссылка-приглашение
`t.me/<бот>?startapp=art_<токен>` (статья добавится получателю при открытии)
и **публичная ссылка для скачивания** `…/dl/articles/<токен>` — отдаёт .md
без авторизации, работает у кого угодно. Лимит статьи — 1 МБ.
**Поиск** в двух режимах: «названия и категории» (мгновенно, по дереву) и
«по содержимому» (сервер, со сниппетом вокруг совпадения; ищет и в доступных
категориях). **Шаринг целой категории** — доступом, без дублирования
контента (`articles_folder_shares`): получатель видит поддерево владельца
вживую (обновления автоматически), read-only (в меню только «скачать»),
секция «📥 Доступные мне»; владелец управляет списком доступа в настройках
категории, получатель может убрать категорию у себя. **Редактор — на весь
экран** (заголовок, категория, растянутое поле текста), в шапке кнопка «?»
со шпаргалкой по Markdown-разметке.

**Articles v2 (v2.17):**
- меню ⋮ дополнено: *копировать* (вся статья в буфер + тост «Скопировано»),
  *информация* (размер Б/КБ/МБ, число символов, даты создания/изменения),
  *история*;
- **история изменений как git**: при каждом сохранении с изменённым текстом
  старая версия уходит в `article_revisions` (хранятся последние 30);
  экран истории показывает список ревизий (дата + размер), клик — diff
  «что изменилось с той версии до текущей» (построчный LCS с контекстом,
  `src/apps/articles/diff.ts`, +зелёным/−красным);
- **публичная ссылка на чтение**: `…/read/<токен>` (read_token, отдельный от
  скачивания) — SPA-роут `/read/:token` рендерит статью в браузере без
  авторизации (JSON с `GET /api/v1/articles/public/{token}` вне auth);
- **позиция чтения**: читалка запоминает долю прокрутки на сервере
  (`article_read_positions`, PUT /articles/{id}/read-pos, debounce 800 мс
  + сохранение при закрытии) и восстанавливает при открытии;
- **двойной тап** по тексту в читалке открывает редактор, прокрученный к
  этому месту (поиск начала тапнутого блока в сыром Markdown, курсор туда);
- **картинки**: кнопка 🖼 в редакторе загружает файл (jpeg/png/webp/gif,
  до 5 МБ) на `POST /articles/images` → `data/articles/<random>.<ext>`,
  раздаётся публично `/uploads/articles/`; в текст вставляется
  `![картинка](/app/habits/uploads/articles/…)`, рендерится `<img>`.

### 🖥 Servers (`/servers`) — по умолчанию скрыта
Мониторинг серверов; видимость по умолчанию «персональный доступ» (выдаёт
админ). «Добавить сервер» — имя + адрес агента (+ опциональный токен).
На каждый сервер ставится **habits-agent** (`habits/agent`, один статический
бинарник, только stdlib и /proc): отдаёт `GET /metrics` с ОС, внешним IP,
uptime, CPU (%, ядра, load1), RAM и списком дисков (всего/свободно);
защита — `Authorization: Bearer <токен>`. Бэкенд-поллер опрашивает адреса
раз в минуту, хранит снапшот и историю CPU/RAM за 48 ч. Карточка сервера:
статус-точка, метаданные, **графики CPU и RAM за 24 ч**, диски с
прогресс-барами (красный от 85 %), ошибки опроса, ручное обновление 🔄.
Установка агента: `deployment/streaks/deploy-agent.sh` (systemd, порт 9101
открыт только докер-подсетям).

**Компактный режим (v2.21)** — переключатель справа над списком (клиентская
настройка в `localStorage`, ключ `servers_compact`): скрывает строку
метаданных, объединяет CPU и RAM в один совмещённый график без подписей
(`ComboChart`) и показывает диски компактно (тонкие бары). Подробный режим —
две отдельные спарклайн-карточки, как раньше.

**Пороговые уведомления по серверу (v2.21, диски по-раздельно v2.22)** — в
настройках сервера (⚙️) раздел «🔔 Уведомлять о лимитах»: **диски по каждой
точке монтирования отдельно** (чекбокс «мониторить» + свой порог свободного
места в ГБ на каждый раздел — чтобы не алертить `/boot/efi` и подобные); RAM
выше N % дольше M минут; CPU выше N % дольше M минут. Пороги хранятся в
столбцах `servers` (`alerts_enabled`, `disk_rules` JSONB `[{mount,min_free_mb}]`,
`disk_min_free_mb` — порог по умолчанию для UI, `ram_pct`/`ram_minutes`,
`cpu_pct`/`cpu_minutes`). Поллер раз в минуту оценивает условия: каждый
мониторимый диск — по последнему снапшоту, RAM/CPU — по устойчивому превышению
на всём окне (`server_samples`, покрытие ≥ 70 % окна). Одно сообщение на
событие: по дискам — множество точек в алерте (`disk_alerted_mounts` JSONB,
сообщение на каждую точку), по RAM/CPU — флаги `ram_alerted`/`cpu_alerted`; при
возврате в норму — «🟢 … в норме». Offline-серверы не оцениваются (устаревшие
данные). Изменение порогов сбрасывает состояние алертов.

**Домашние машины (push-режим, v2.16)** — для машин без внешнего IP.
При добавлении выбирается «🏠 Домашняя машина»: сервер генерирует
`push_token` и показывает команду установки. Агент с заданным
`AGENT_PUSH_URL` сам шлёт тот же JSON-отчёт раз в `AGENT_PUSH_INTERVAL`
(60 с) на `POST /api/v1/agent/push` (вне tma-авторизации, Bearer =
push-токен); входящие порты не нужны, HTTP-сервер агента поднимается
только при явном `AGENT_ADDR`. Поллер такие машины не опрашивает.
Карточка — та же (бейдж 🏠, без кнопки 🔄), online = отчёт моложе 3 минут.
Установка: однострочник из публичного репо агента
(`curl -fsSL …habits-agent/main/install-home.sh | sudo bash -s -- <токен>`,
бинарник берётся из GitHub-релиза) или `deployment/streaks/install-home-agent.sh`
локально из монорепо (сборка из исходников). Публичный репозиторий агента —
github.com/resagera/habits-agent (main.go синхронизируется с `habits/agent`,
релизы с бинарниками amd64/arm64).

**Offline/online-уведомления ботом (v2.16)** — для всех серверов (pull и
push): если `last_ok_at` старше 3 минут, владельцу приходит одно сообщение
«🔴 не выходит на связь» (флаг `offline_notified` защищает от повторов),
при первом удачном отчёте/опросе — «🟢 снова на связи». Серверы, ни разу
не выходившие на связь, не алертятся.

### 🔐 Сейф (`/vault`) — по умолчанию скрыта, v2.84
Файлы, зашифрованные **на устройстве**: сервер хранит только шифробайты и
конверты ключей и не может ни прочитать файл, ни узнать его имя и тип.
Подробный план и принятые решения — `habits/PLAN-vault.md`.

- **Схема ключей**: пароль → PBKDF2-SHA256 (310k) → KEK разворачивает ключ
  папки FK; у каждого файла свой ключ содержимого CK, обёрнутый FK
  (`key_env`), метаданные (имя, тип, размер) — тоже под FK (`meta_env`).
  Смена пароля переписывает одну обёртку FK, перенос файла между папками —
  32 байта CK; перешифровывать файлы не нужно. Отдельной проверки пароля
  нет: GCM-тег на обёртке FK и есть проверка.
- **У каждой папки свой salt и своя обёртка**, даже при одинаковом пароле:
  расшаренную подпапку получатель открывает, не имея доступа к родителю.
- **Формат блоба**: `HVLT` + версия + размер чанка + база IV, дальше чанки по
  4 МБ, каждый AES-GCM с IV = база ‖ счётчик. Чанки нужны не ради скорости:
  файл целиком живёт в памяти в трёх копиях, и на телефоне это смертельно.
- **Загрузка**: `POST /vault/uploads` (init, проверка лимитов ДО записи на
  диск) → `.../chunk` сырыми байтами → `.../finish` (конверты, превью).
  Одним потоковым запросом нельзя: `fetch` с `ReadableStream` в теле требует
  HTTP/2 и не работает в Safari.
- **Замок**: ключи в `Map` в памяти страницы, TTL 60 с с продлением на каждое
  действие, 🔒 на папке и «запереть всё», автозамок на `visibilitychange` и
  при уходе со страницы. Ключ — неизвлекаемый `CryptoKey`; строка пароля
  живёт столько же и нужна для автооткрытия соседних папок с тем же паролем.
  При запирании отзываются blob-URL и забываются расшифрованные имена.
- **Просмотр**: картинки, текст (до 1 МБ показа), аудио, видео — на месте;
  PDF в браузере через `<iframe>`, а в вебвью Telegram не рисуется, поэтому
  там кнопка «Открыть в браузере» (`/vault?file=<id>`, пароль спросят заново).
  Остальное — скачиванием; внутри Telegram оно ненадёжно (ограничение
  вебвью), и об этом честно говорится тостом.
- **Превью** для картинок делает клиент (canvas → webp) и шифрует тем же CK;
  включается ТОЛЬКО при создании папки: сервер их построить не может, а
  достроить задним числом нечем.
- **Лимиты** по типу пользователя (`user_type_limits.vault_file_mb`,
  `vault_total_mb`, правятся в админке): regular 3/10 МБ, payed1 10/300,
  payed2 50/1024, vip 50/1024. Квота считается **владельцу** и проверяется
  дважды — на init по заявленному размеру и на finish по факту.
- **Шаринг** (`vault_shares`, kind folder|file) — доступ, а не копия: тот же
  шифротекст, открыть можно только зная пароль, и уведомление бота об этом
  прямо говорит. Владелец удалил файл — он пропал у всех.
- **Удаление сразу**, без корзины: место в сейфе маленькое, а корзина
  занимала бы квоту.
- **Пароль не восстанавливается** — ключа восстановления сознательно нет.

### 📁 My Files (`/files`) — по умолчанию скрыта, v2.18
Доступ к папкам на домашних машинах из телефона; видимость «персональный
доступ» (как Servers). «Добавить машину» — имя, сервер генерирует токен и
показывает команду установки. На машину ставится **habits-files-agent**
(`habits/files-agent`, отдельный бинарник, gorilla/websocket): в его конфиге
`FILES_AGENT_ROOTS` перечисляются папки в виде `путь:ro|rw` через `;` — режим
`ro` (только чтение) или `rw` (чтение и запись). Любой путь запроса
проверяется на принадлежность одной из папок; выход за их пределы (в т.ч.
через `..` и симлинки) запрещён, запись в `ro`-папку отклоняется.

**Транспорт.** У домашних машин нет внешнего IP, поэтому агент держит
**исходящий WebSocket** на `GET /api/v1/files/agent` (вне tma-авторизации,
Bearer = токен машины); первым кадром шлёт `hello` со списком папок (они
кэшируются в БД для показа). Бэкенд — релей (`internal/files`): пришедший от
UI HTTP-запрос спаривается с этим соединением по id машины. Протокол
запрос/ответ мультиплексируется по `id`; данные чтения приходят **бинарными
кадрами** (8-байтовый префикс = id запроса), управляющие ответы — JSON.
Одно активное соединение на машину (новое вытесняет старое), ping/pong
каждые 30 с, реконнект агента с экспоненциальным бэкоффом.

**UI.** Карточка машины со статус-точкой (online = отчёт агента активен),
сворачивается. Внутри — браузер папок с хлебными крошками; клик по папке
углубляется, по файлу — открывает просмотр. Просмотр: тексты (`<pre>`, до
2 МБ), картинки (`<img>`), музыка (`<audio>`), видео (`<video>`), PDF
(`<iframe>`) — всё **потоком через бэкенд** с поддержкой HTTP Range (перемотка
видео/аудио, дозагрузка). В `rw`-папках: загрузка файла (сырым телом,
бэкенд пишет чанками по 512 КБ), создание папки, переименование, удаление;
у каждой записи меню ⋮ (скачать/переименовать/удалить).

**Стриминг-пропуски.** `<video>/<audio>/<img>` в вебвью не шлют заголовок
`Authorization`, поэтому UI сначала запрашивает `POST /files/machines/{id}/ticket`
(bound к машине и пути), получает одноразовый токен и грузит файл по
`GET /api/v1/files/stream/{ticket}` (вне tma-авторизации, авторизация — сам
пропуск, TTL 6 ч). Отдача — с `Accept-Ranges`, `Content-Range`,
`Content-Disposition` (для скачивания); бэкенд читает у агента чанками и
пишет в ответ с backpressure.

Установка: однострочник из репо агента
(`curl -fsSL …habits-agent/main/install-files.sh | sudo bash -s -- <токен> "<папки>"`).

### ⌨️ Terminal (`/terminal`) — по умолчанию скрыта, v2.20
Веб-консоль (shell) к домашней машине из любой точки; видимость «персональный
доступ». «Добавить машину» — имя, сервер генерирует токен и команду установки.
На машину ставится **habits-term-agent** (`habits/term-agent`, gorilla/websocket
+ creack/pty): держит **исходящий WebSocket** на `GET /api/v1/terminal/agent`
(вне tma-авторизации, Bearer = токен машины) и по запросу открывает PTY —
`bash -l` от пользователя агента (переменная `TERM=xterm-256color`, стартовый
каталог настраивается).

**Транспорт.** Бэкенд-релей (`internal/terminal`) мультиплексирует несколько
сессий по одному WS агента: у каждой свой id, кадры данных бинарные с
8-байтовым префиксом-id, управляющие (`open`/`resize`/`close`/`exit`) — JSON.
Браузер открывает свой WebSocket `GET /api/v1/terminal/stream/{ticket}` (вне
tma-авторизации; ticket одноразовый, TTL 60 с, выдаётся `POST
/terminal/machines/{id}/session` владельцу онлайн-машины). Кадры браузера:
бинарные — stdin, текстовые — `{"t":"resize",cols,rows}`; к браузеру бинарные —
stdout PTY. Хаб на медленном клиенте притормаживает агента (блокирующая
пересылка), при разрыве клиента — шлёт агенту `close`, тот убивает PTY.

**UI.** Терминал — **xterm.js** (ленивый чанк) на весь экран: реальный bash с
цветами, автодополнением, редакторами (vim/nano), запуском `claude` и т.п.
Внизу — панель спецклавиш для мобильной клавиатуры (Esc, Tab, стрелки, ^C/^D/
^Z/^L, `|~/`, и «липкий» Ctrl: следующая буква → Ctrl-символ). Ресайз по
FitAddon шлёт `resize`; при обрыве — кнопка переподключения (новый ticket).

**⚠️ Безопасность.** Полный доступ к shell под пользователем агента. Гарантии:
страница персональная (по умолчанию только админ), токен машины = секрет,
ticket одноразовый. Ставить только на свои машины.

Установка: `curl -fsSL …habits-agent/main/install-term.sh | sudo bash -s -- <токен>`.

запись попадает во «Входящие» на странице Contacts (бот шлёт «хочет
поделиться…»), где её можно **принять** (копия/доступ создаются в этот момент;

автоматически — расшифровка только на устройстве).

### 📦 Projects (`/projects`) — v2.26
Проекты-сборники: проект состоит из **блоков** — текст (обычный или rich

прогресс), статья Articles (спойлером, рендер Markdown), задача и категория
задач Tasks (статус, приоритет, срок, чек-лист). Ref-блоки **резолвятся при
каждой загрузке** проекта (данные всегда свежие; при открытом проекте —
автообновление раз в 60 с); при добавлении можно выбрать существующий элемент
или создать новый (`create_name`) — он появится и на своей странице. Блоки
вставляются на любую позицию («＋ Блок ниже», позиции сдвигаются), текстовый
блок **разбивается по курсору** на два, у блока настраиваемый фон (color),
спойлер-состояние `collapsed` хранится на сервере. Проекты **сворачиваются**
(блоки не грузятся, пока проект свёрнут — список отдаёт только метаданные),
группируются в **категории** (сворачиваемые; проекты вне категорий — общий
список). **Параметры проекта**: название, описание, иконка-эмодзи, цвет,
обложка (upload), тип (текст + подсказки из предустановленных
рабочий/личный/разработка/обучение/мероприятие/покупки и уже упомянутых),
статус (draft/planned/active/paused/done/cancelled/archived), теги, даты
начала/планового завершения, часовой пояс, владелец и даты создания/изменения
(отображаются). **Совместный доступ** — через `deliverShare` (kind `project`,
контакт с галочкой — сразу, иначе «Входящие» Contacts); участники добавляют и
редактируют блоки, параметры и удаление — у владельца, участник может
покинуть. **История изменений** (`project_history`): кто и что добавил,
изменил или удалил (создание, параметры, блоки, участники). Если проект
изменил другой участник после вашего последнего просмотра — в списке красная
★ (`project_views`, отметка при открытии). Файлы — в
`DATA_DIR/projects` (`/uploads/projects/`), при удалении блока/проекта
чистятся с диска (вместе с учётом в `project_uploads`).

**Лимиты и типы пользователей (v2.27)**: у каждого пользователя есть тип —
`regular` (по умолчанию), `vip`, `payed1`, `payed2`; тип назначает админ в
карточке пользователя (Settings → Пользователи). На каждый тип — свои лимиты
(`user_type_limits`, редактируются админом в секции «📐 Лимиты Projects по
типам»): **блоков в одном проекте** (по умолчанию 100, считается по владельцу
проекта), **картинок и файлов суммарно на пользователя** (учёт —
`project_uploads`, запись снимается при удалении блока/проекта), **размер
одной картинки и одного файла в МБ**. Превышение — 400 с человекочитаемым
сообщением (показывается тостом). Кнопка «＋ Блок» есть и сверху списка
блоков (вставка в самое начало), и снизу.

`?tab=`, восстанавливается после обновления): **Дневник** (по умолчанию),
**План**, **Общие**, **Рецепты**, **Статистика**.

**Дневник**: выбор дня (← → , «Сегодня», календарь), сводка дня с
прогресс-барами калорий и БЖУ (цель/остаток; превышение не обрезается —
красный бар + текст «превышение N»), приёмы пищи группами
завтрак/обед/ужин/перекусы/без категории с итогами группы. Запись: название,
время, описание, фото, состав из продуктов; бейджи 📋/📖 — создана из
шаблона/рецепта. Действия (⋮): редактировать, дублировать, перенести на
дату, сохранить как шаблон, создать рецепт, удалить (с подтверждением).
Запись без состава — ручные КБЖУ.

**Продукты**: личный каталог (название, альт. название, производитель,
категория, фото, КБЖУ на 100 г или 100 мл, вес 1 шт и 1 порции). Поиск в
форме добавления (debounce, недавние/частые — первыми: `used_count`,
`last_used_at`), создание нового продукта прямо из поиска. DELETE
использованного в истории продукта архивирует его (физически не удаляется),
неиспользованного — удаляет. Управление каталогом — на вкладке Рецепты.

**Снимки (архитектурное требование)**: элемент записи/шаблона/рецепта хранит
СНИМОК данных продукта (название, количество, единица, вес, КБЖУ на 100 г и
итоги) — изменение глобального продукта, шаблона или рецепта не меняет
старые записи дневника. Итоги пересчитываются на сервере из снимков
(`grams/100 × per100`), округление — только при отображении.

**Единицы**: г, мл, шт, порции. Для шт/порций вес берётся из продукта
(`piece_grams`/`portion_grams`); если не задан — фактический вес вводится
вручную.

**Профиль и цели (⚙️, onboarding при первом заходе без профиля)**: пол, дата
рождения, рост, вес, целевой вес, % жира, активность
(min/low/medium/high/max — коэффициенты 1.2…1.9 в конфиге
`store.FoodActivityCoef`), цель (похудение/поддержание/набор) с
дефицитом/профицитом. Расчёт: BMR по Mifflin–St Jeor → TDEE → коррекция;
белок = база (текущий/целевой вес, безжировая масса по % жира или ручной
вес) × коэффициент г/кг; жиры 30% калорий, углеводы — остаток. Расчёт
показывается с объяснением (details), можно переопределить вручную;
дисклеймер «не заменяет медицинские рекомендации». Цели хранятся
**периодами** (`food_goals`): новая цель закрывает прошлый период днём
раньше — прошлые даты и статистика считаются по цели своего периода.

**Шаблоны** — приём пищи без даты (создаются из записи или вручную),
добавляются в дневник в один тап (снимок текущего состава, фото
переиспользуется — файл один). **Рецепты**: ингредиенты, шаги, итоговый вес
и порции → КБЖУ на 100 г и на порцию; в дневник — по съеденному весу (нужен
итоговый вес) или по порциям.

**Общие**: доступ к дневнику для другого пользователя через deliverShare
(kind `food`, только чтение) с флагами видимости: цели, фото, описания, вес
— проверяются на бэкенде (`food_shares`). Разделы «Доступны мне» (просмотр
чужого дневника по дням) и «Мой дневник доступен» (флаги, отзыв).

**Статистика**: 7/14/30 дней или произвольный период; карточки (средние
КБЖУ, заполненные дни, % выполнения целей, дни сверх/в рамках) и графики
(SVG): калории с линией цели и средним за 7 дней (превышение — красным),
белки с целью, жиры, углеводы, число приёмов, распределение калорий по
приёмам (стек). Слой для будущей интеграции с Metrics:
`GET /food/metrics/{key}` с ключами `food.calories.daily`,
`food.protein.daily`, `food.fat.daily`, `food.carbs.daily`,
`food.meals.count`, `food.goal.calories`, `food.goal.protein`,
`food.goal.calories_completion`, `food.goal.protein_completion`.

**Фото** — только изображения (проверка MIME) до 10 МБ, случайные имена, в
`DATA_DIR/food` (`/uploads/food/`); один файл может использоваться шаблоном
и несколькими записями — физически удаляется только когда ссылок не осталось
(`FoodPhotoRefCount`). **Фото в плане питания нет намеренно** — иначе
подсчёт ссылок пришлось бы расширять на слоты плана.

#### 📅 План питания (вкладка «План», v2.55)

Меню на N дней вперёд (1…90, обычно 7 или 14), возможно приблизительное и на
нескольких участников.

**Ключевое отличие от дневника: план — «намерение», дневник — «факт».** Запись
дневника/шаблон/рецепт хранят СНИМОК продукта; позиция плана хранит **ссылку**
(`kind` + `ref_id`) плюс **кэш КБЖУ**. При переносе дня в дневник создаётся
свежий снимок — дальнейшие правки плана записи дневника не трогают. КБЖУ своих
продуктов на момент переноса берутся актуальные (чужие ссылки не разрешаются —
это раскрыло бы чужие данные).

**Три уровня точности позиции** — это и есть «примерно/ориентировочно»:
`kind='free'` — свободный текст («что-нибудь мясное»); `approx=true` со ссылкой —
продукт/рецепт без количества; `approx=false` — количество задано, КБЖУ
считается. Приблизительные позиции в сумму НЕ входят; сводка дня отдаёт
`counted`/`approx`, а UI показывает «посчитано 6 из 9» — неполная сумма никогда
не выдаётся за точную. Свободная позиция может нести ручные КБЖУ (`approx=false`
без ссылки) — так же выглядят копии плана, полученные по ссылке.

**Дни — по индексу, не по дате.** Слот привязан к `day_index` (0-based), у плана
опциональная `start_date`; без неё план «шаблонный» и применяется к любой дате.
Поэтому план можно сдвигать, продлевать и копировать неделю в неделю. Уменьшение
`days` слоты за границей не удаляет (и в сводку они не попадают) — вернув длину,
пользователь получает их обратно.

**Участники** (`food_plan_participants`) — именованные лица (жена, ребёнок),
`user_id` необязателен. У каждого коэффициент порции и своя цель по калориям.
Привязка к аккаунту Habits (`PUT …/participants/{pid}` с полем `user` — id или
`@username`, пустая строка снимает) нужна, чтобы человек открыл план у себя и
перенёс СВОИ порции в свой дневник: сервер отдаёт `is_me`/`user_label`, а
перенос по умолчанию выбирает участника-себя. **PUT участника частичный** —
поля, которых нет в запросе, берутся из текущих (иначе правка имени молча
снимала бы привязку).
Слот с `participant_id = NULL` — **общий**: входит в итог каждого участника со
его коэффициентом; личный слот — только в итог своего участника и без
коэффициента. Итог дня = сумма по участникам (без участников — простая сумма).
Сводка считается в Go (`foodPlanSummary`) и отдаётся вместе с планом.

**Перенос в дневник** (`POST /food/plans/{id}/apply`) — слот → запись дневника
(`source_type='plan'`, `source_id` = id плана). Записи создаются **только в своём
дневнике**: участник открывает общий план у себя и применяет сам — в чужой
дневник план не пишет никогда. Приблизительные позиции уходят строкой «Примерно:
…» в описание, чтобы не потеряться. `mode`: `''` — проверка (при `existing > 0`
ничего не создаётся, UI спрашивает), `add` — поверх, `replace` — заменить прежние
записи из этого плана на этих датах.

**Шаринг** — два канала, как принято в проекте: через контакт (`deliverShare`,
kind `food_plan`) — **доступ** к тому же плану, `food_plan_shares.can_edit`
включает правку состава (участники, шаринг и удаление остаются за владельцем);
по ссылке `startapp=fpl_<token>` — независимая **копия** (ссылки на продукты и
рецепты снимаются, названия и КБЖУ сохраняются).

**Подсказка в Дневнике**: `GET /food/plans/today?date=` отдаёт планы (свои и
открытые мне), у которых дата попадает в период — с днём, слотами (общие + мои
как участника) и числом уже перенесённых записей. Дневник показывает карточку
«📅 По плану…» с кнопкой переноса. Планы без `start_date` сюда не попадают: их
день к дате не привязан.

**Лимиты**: 90 дней, 10 участников, 500 слотов на план, 50 позиций в слоте.

**UI**: две недели × четыре приёма в сетку на телефоне не влезают — вертикальный
список дней с переключателем недель, день раскрывается по тапу. Раскрытые дни
хранятся на сервере (`ui_collapsed`, ключ приложения `food_plan_open`; день
кодируется как `planId * 100 + dayIndex` — day_index заведомо < 100). Копировать
можно и один день, и неделю целиком (кнопка ⧉ у переключателя недель). В шапке
дня показывается цель смотрящего (`goal_calories`) — но только у плана без
участников, у остальных осмысленны цели участников.

### 🤖 Автоматизация (`/automation`) — v2.29

Автоматизированные действия по расписанию или вручную. Страница
`visibility=personal` (по умолчанию только админ, доступ выдаётся в админке).
Первый и пока единственный тип — **заказ воды на jur.am** (`kind=jur_water`).

**Сетевой выход через домашний агент.** jur.am за Cloudflare, который отдаёт
датацентр-IP прод-сервера 403-челлендж (даже на главной, с любым UA). Поэтому
HTTP-запросы к jur.am **туннелируются через агента на домашней машине**
(резидентный IP проходит). Вся логика сценария остаётся на проде — агент
`habits/automation-agent` (public repo `habits-agent`, subdir `automation-agent`)
держит исходящий WS `GET /api/v1/automation/agent` (Bearer-токен из
`automation_agents`, вне tma-auth) и выполняет одиночные HTTP-запросы к белому
списку (`jur.am`), возвращая ответ как есть (без своих cookie и без следования
редиректам — этим управляет сервер). Прод-хаб `internal/egress` даёт
`http.RoundTripper`, который сериализует запрос в WS-кадр; cookie-jar и
редиректы `jurwater` работают прозрачно поверх туннеля. Без активного агента
запуск невозможен (`Execute` вернёт «домашний агент не в сети»; воркер
откладывает срабатывание на час и шлёт предупреждение). Токен и команда
установки — в карточке (`GET /automation/agent-info`), статус online —
`hub.Online(userID)`.

**Исполнитель** (`internal/jurwater`, `Transport` = релей-транспорт агента)
выполняет сценарий обычными HTTP-запросами с cookie-сессией, **без
headless-браузера** (jur.am — Magento 2 + кастомный модуль `Jur_Checkout`).
Шаги: логин (`/customer/account/loginPost`,
form_key берётся со свежей страницы корзины — Magento меняет его после входа) →
очистка корзины → добавление N бутылей «Макур Джур 19л» (product 465, форма
`/checkout/cart/add`) → чтение долга возвратной тары из CRM
(`/crmintegration/index/bottlesdebt` → `makurJur19`) → адрес и время доставки
(`/rest/ru/V1/carts/mine/shipping-information` с
`extension_attributes.mp_delivery_date/mp_delivery_time`, дата — ближайшая
доступная из `custom_date_off_checkout`, слот — первый из
`custom_time_checkout`) → возвратная тара (кастомный
`/checkoutjur/quote/index`, поле `makurmec`) → оформление наличными
(`/rest/ru/V1/carts/mine/payment-information`, метод `checkmo`). В **dry-run**
последний шаг пропускается (доходит до оформления, заказ не создаётся). Каждый
шаг пишется в лог `[{name, ok, detail}]`.
Шаг оформления считается успешным, **только если сайт вернул числовой номер
заказа** (Magento отдаёт голый id); при 200 с не-числовым телом (null/ошибка)
шаг падает с сырым ответом — иначе «нет ошибок, но и заказа нет» (безопасно для
повтора: заказ не создан). Шаг «сессия» при отсутствии `form_key` различает
Cloudflare-challenge/403 от прочего (по коду и телу) для понятной причины.

**Карточка** (`automations`): логин/пароль сайта (шифруются AES-256-GCM,
ключ — `AUTOMATION_KEY` или производный от `BOT_TOKEN`; наружу отдаётся только
маскированный логин и `has_creds`), количество бутылей, режим тары
(`auto` — из CRM / `fixed`), слот времени (`first`/конкретный), метод оплаты,
комментарий, интервал повтора (дней) и `next_run_at` (NULL — только вручную).

**Планировщик** (`internal/automation`, тик 1 мин): за сутки и за час до
`next_run_at` шлёт уведомление в бот (`notified_day`/`notified_hour`, чтобы не
дублировать), по наступлению срока — запускает; при успехе реального запуска
планирует следующий (`+interval_days`) и сбрасывает флаги. Ручной запуск и
dry-run идут через тот же `Execute` (лок `running` от параллельного запуска),
выполняются синхронно в HTTP-запросе, результат — в историю (`automation_runs`)
и уведомлением в бот. Первый реальный заказ рекомендуется сделать кнопкой
«Запустить» вручную.

### 📬 Почта (`/mail`) — v2.71, personal
Свой приём почты на `resager.ru`: письма попадают прямо в базу приложения.
**Это не почтовый сервер общего назначения** — ящиков, IMAP и отправки нет.
Цель — читать и разбирать письма приложением (чеки магазинов для Finance), а
Postfix+Dovecot заняли бы 1–1.5 ГБ из 2.3 свободных и дали бы несопоставимую
поверхность атаки.

- **Приёмник** — `internal/smtpd` на stdlib. `net/textproto` даёт `DotReader`
  со снятием точечного экранирования — единственное по-настоящему хитрое место
  протокола. Внутри контейнера слушается `:2525` (приложение работает не от
  root), порт 25 пробрасывает docker (`ports: 25:2525` — единственный
  публикуемый порт стека).
- **Защита, от дешёвого к дорогому**: блокировка IP по памяти → пауза 1.5 с
  перед баннером и разрыв, если клиент **заговорил первым** (боты так делают,
  законные серверы — нет) → лимиты подключений (60/ч) и писем (30/ч) на IP →
  `SIZE` в MAIL FROM → отказ отправителю с нерезолвимым доменом → **RCPT TO по
  белому списку** (главный барьер: словарный перебор не доходит до DATA) →
  `only_from` у алиаса → лимит письма 15 МБ, получателей 5, ошибок 5, команд
  50. **Ретрансляции нет ни при каких условиях**; `AUTH` отвечает 502
  намеренно (через нас отправлять нельзя вообще), `VRFY` — 252: подтверждать
  существование адресов значит помогать перебору.
- **Блокировки растут**: час → 6 часов → сутки. Хранятся в памяти и в
  `mail_ip_stats`, при старте поднимаются обратно. ⚠️ Снимать надо **и в
  памяти**: `smtpd.Server.Unblock` пробрасывается в роутер через
  `httpapi.MailInfo.Unblock` — иначе кнопка чистила бы только базу.
- **Спам-оценка** (порог 6, письмо помечается, но НЕ удаляется): нет PTR или
  FCrDNS не сходится, HELO без домена либо выдающий себя за нас, отсутствие
  Message-ID/Date, отсутствие TLS, SPF. **SPF упрощён** (ip4/ip6/a/mx/include/
  all, ≤10 запросов, глубина 3) и идёт ТОЛЬКО в оценку: отклонять по нему
  нельзя — законные пересылки ломают SPF штатно.
- **STARTTLS** с самоподписанным сертификатом (лежит в `DATA_DIR/mail/tls`, не
  перевыпускается на каждый старт): для входящей почты действует
  оппортунистический TLS (RFC 7435), сертификат отправители не проверяют.
  `MAIL_TLS_CERT`/`MAIL_TLS_KEY` подменяют его настоящим.
- **Разбор MIME** — stdlib + `x/text` для перекодировки: windows-1251 и koi8-r
  в русских магазинах живее всех живых. Исходник письма кладётся на диск
  (`DATA_DIR/mail/ГГГГ/ММ`), тела — в базу с обрезкой: разбор можно повторить
  новым кодом, не потеряв оригинал.
- **HTML письма — только в песочнице**: `iframe sandbox=""` + CSP
  `default-src 'none'`, картинки включаются кнопкой (в рассылках это маячки,
  сообщающие отправителю об открытии). Вложения отдаются через API с проверкой
  владельца и всегда как `attachment` — HTML из письма не должен исполниться на
  нашем домене.
- **Адреса и алиасы** (`mail_addresses`): постоянный адрес или одноразовый
  алиас под магазин с автогенерацией имени (`ozon-a7f3@`) и `only_from`.
- **Таблицы**: `mail_addresses`, `mail_messages`, `mail_attachments`,
  `mail_ip_stats` (счётчики по IP, а не журнал событий — порт 25 перебирают
  круглосуточно, построчный лог занял бы больше места, чем сама почта) +
  `user_settings.mail_notify` — миграция 0087.
- **API**: `GET /mail/overview`, `GET /mail/messages/{id}`,
  `POST /mail/messages/{id}/flag|archive`, `DELETE /mail/messages/{id}`,
  `GET /mail/attachments/{id}`, `GET|POST /mail/addresses`,
  `PUT|DELETE /mail/addresses/{id}`, `GET /mail/guard`,
  `POST /mail/guard/{ip}/unblock`, `PUT /mail/settings`,
  `PUT /mail/addresses/{id}/parser`, `POST /mail/messages/{id}/parse`
  (`{"refresh":true}` — перечитать уже разобранный чек поумневшим разбором),
  `GET /mail/receipts/{id}/items`, `DELETE /mail/receipts/{id}`.
- **Чеки магазинов → траты Finance** (v2.71, фаза 5 плана Finance). У адреса
  включается разборщик (`mail_addresses.parser`) и выбираются категория и счёт;
  письмо на этот адрес разбирается на лету, письма «до настройки» — кнопкой в
  письме (`POST /mail/messages/{id}/parse`).
  - Разбор — `internal/receipts`, по **текстовой** части письма: вёрстка
    рассылок меняется от кампании к кампании, текстовая версия у магазина
    годами одна. Учтены оба вида пересылки — Gmail и Apple Mail (цитирование
    «> » снимается на любую глубину). Имя позиции **жадное**: разделитель
    « x » берётся последним, иначе «Item x 2 x 3 100.00֏» разобралось бы как
    количество 2 с единицей «x».
  - **В Finance уходит ОДНА трата на итог чека**, а не позиция за позицией:
    поход в магазин — одна трата. Сумма — именно `Total`: позиции магазин
    показывает по каталожным ценам, и с итогом они не сходятся (вес, скидки).
  - **Идемпотентность двойная**: `unique (user_id, parser, order_no)` и
    `finance_transactions.external_id` = `yerevancity:3424178`. Чек без номера
    заказа отклоняется — иначе от повторов защититься нечем.
  - ⚠️ **Дата траты — `mail_receipts.purchased_on DATE`**, отдельной колонкой:
    `timestamptz` читается в зоне сессии, и покупка в 23:23 по Еревану уезжала
    в трату следующего дня.
  - **Доступ — персональная опция** `mail.receipts` (`FeaturesRegistry` +
    `feature_access`, выдаётся в Админке; админ проходит всегда). Чек попадает
    в финансы **владельца адреса** (`mail_addresses.user_id`). Без опции письмо
    принимается, но не разбирается.
  - Импортёр — `internal/receiptimport`: нужен и приёмнику почты, и HTTP.
    Зависимости приёмника проставляются в `main` ДО запуска — иначе поле
    читается из чужой горутины.
  - **Счёт списания берётся из письма**, если оно его называет, и только иначе —
    из настроек адреса: последние 4 цифры карты («•••• 6307») ищутся в названии
    и заметке счёта, «Наличные»/«cash» — по `kind = 'cash'`. Отдельного поля
    «номер карты» ради одной подстроки не заводили. Не нашли — оставляем счёт
    по умолчанию: приписать трату не тому кошельку хуже, чем никакому.
  - Таблицы `mail_receipts` / `mail_receipt_items` — миграция 0089,
    `mail_receipts.note` — 0097.
- **Разборщики** (`receipts.Parsers`, новый магазин = функция + строка в списке,
  интерфейс подхватит сам):
  - `yerevancity` — «Order #… delivered», чек магазина со списком позиций.
  - `yandexgo` — «Яндекс Go — отчёт о поездке» (v2.74). **Позиций у поездки
    нет**, и это не недоработка: делить поездку по группам товаров нечего.
    Вместо позиций — `mail_receipts.note`: маршрут с временами, машина и номер,
    тариф, время и расстояние, способ оплаты, перевозчик и водитель; заметка
    целиком уезжает в `finance_transactions.note`. Раз позиций нет, `Resplit`
    оставляет трату без долей, и в отчёт она идёт своей категорией.
  - ⚠️ **Номера заказа в отчёте о поездке нет**, а защита от повторной
    пересылки нужна: `order_no` собирается из даты и времени подачи
    (`20260806-1429`) — две поездки не начинаются в одну минуту.
  - Разбор идёт по «сжатому» списку строк (пустые строки, `[image: …]` и голые
    ссылки выброшены): письмо свёрстано таблицей, и число пустых строк между
    подписью и значением от письма к письму гуляет. Дата — «6 августа 2026 г.»
    своим разбором русских месяцев, при обрезанном теле берётся из темы. Без
    итога **или без даты** — `ErrNotReceipt`: трата без даты молча уехала бы на
    сегодня. Валюта определяется по знаку (֏/₽/₸/₾/$/€) — Go работает в разных
    странах, и валюта в отчёте обозначена только знаком.
- **DNS (настраивается вручную в reg.ru)**: `MX resager.ru → mail.resager.ru`
  (10), `A mail.resager.ru → 45.129.196.26`, `TXT resager.ru: v=spf1 -all` —
  мы не отправляем почту, поэтому жёсткая запись защищает домен от подделок,
  `TXT _dmarc.resager.ru: v=DMARC1; p=reject`. Для отправки в будущем
  понадобится PTR у IP (сейчас пустой) и DKIM.

### 📺 Пульт ТВ (`/tv`) — v2.75, personal
Просмотр домашних сериалов на ТВ-приставке: агент на компьютере, плеер на
приставке, пульт в телефоне.

- **Прод — ТОЛЬКО шина** (`internal/tvrelay`): пересылает непрозрачный JSON
  внутри комнаты и ничего о нём не знает. Листинги папок приставка берёт у
  своего агента по локальной сети напрямую, поэтому **ни медиа, ни пути файлов
  через сервер не проходят**, а нагрузка на VPS нулевая.
- **Подключение по коду с экрана приставки** (v2.76). Адрес компьютера
  пользователь знать не обязан, а по DHCP он ещё и меняется. Приставка
  показывает 8-значный код (крупно на экране запуска, мелко в углу при
  просмотре); ввод нормализуется — регистр, пробелы и дефисы отбрасываются.
  Алфавит без `0/O/1/I`: код читают с телевизора и набирают на телефоне.
- **Коды живут в памяти шины**, выдаются приставке при входе в комнату и
  снимаются, когда ушёл последний экран — иначе код остался бы годным для
  выключенного телевизора. Повторный вход в ту же комнату отдаёт ПРЕЖНИЙ код:
  перезагрузили страницу на телевизоре — код меняться не должен.
- ⚠️ **Комната — НЕ адрес в локальной сети.** Его раздаёт DHCP, и после
  перезагрузки роутера комната стала бы другой, а сохранённая приставка —
  мёртвой. Ключ = имя машины + случайный хвост, лежит в кэше агента.
  `MEDIA_ROOM` переопределяет вручную; строка нормализуется из
  `http://192.168.0.226/tv/`.
- ⚠️ **Владелец закрепляется за комнатой при первом подключении пульта.** Без
  этого ключ вида «192.168.0.226» угадал бы любой прохожий: приставка сидит в
  локальной сети, а шина стоит на общедоступном сервере. Чужую комнату не
  занять (409), её не видно в списке и не удалить (404).
- **Веб-сокет приставки без авторизации** — её открывают на телевизоре, где
  Telegram нет. Пульт подключается по одноразовому пропуску (`terminal.Tickets`):
  заголовок `Authorization` в веб-сокете из браузера не поставить.
- Пинг раз в 30 с: мобильные сети рвут молчащие соединения, а пульт висит
  открытым весь фильм. Пинг идёт через тот же замок, что и запись — две
  параллельные записи в один веб-сокет это паника в gorilla.
- **Настройки агента** — `~/.config/habits-media-agent.conf` (умолчания → файл
  → переменные окружения). Список папок — длинная строка с разделителями, в
  файле она пишется по папке на строку; окружение остаётся главнее, чтобы
  разовый запуск не требовал правки файла.
- **Агент** — `habits/media-agent` (свой README): слушает `127.0.0.1`, наружу
  его выставляет nginx на 80-м (на роутере нестандартные порты закрыты).
  Разбор ffprobe по требованию с кэшем, ссылки на файлы подписаны HMAC,
  наружу уходят идентификаторы, а не пути.
- **Приставка играет только MP4** (проверено на Xiaomi Mi TV, Chrome 150 в
  WebView): MKV и AVI не открывает, хотя HEVC и 10 бит берёт спокойно. Живого
  перекодирования нет — неподходящее уходит в фоновую очередь ffmpeg, а
  большие библиотеки готовит `tvconvert.py` (он же раскладывает под Plex).
- **Куда играть, решает содержимое файла, а не пожелание пульта**: файл без
  видеодорожки в `<video>` — это чёрный прямоугольник вместо музыки. Логика в
  одной функции `startFrom()`, общей для списка на приставке и для команд с
  пульта, чтобы два пути не разъезжались. Очередь однородная: при выборе серии
  в неё идут только файлы с картинкой, при выборе трека — только без неё;
  `as:"music"` остаётся явным «пустить фильм фоном».
- **Полный экран — свой режим на CSS** (класс `theater`): Fullscreen API в
  вебвью приставки не отрабатывает, а команда с пульта приходит без жеста на
  самом телевизоре, когда браузер его и не разрешил бы. Родной режим пробуем
  следом, необязательным бонусом.
- ⚠️ `play()` у элемента **без источника** не отвергается и не выполняется, а
  висит вечно: разблокировка звука на приставке — это само нажатие, проигрывать
  для неё ничего не нужно.
- **Таблица** `tv_rooms` — миграция 0099.
- **API**: `GET /tv/rooms`, `POST /tv/attach`, `DELETE /tv/rooms/{key}`,
  `GET /tv/socket?room=` (приставка, вне авторизации),
  `GET /tv/remote/{ticket}` (пульт).

### 💰 Finance (`/finance`) — v2.72, personal
Плановые платежи, фактические траты с деревом категорий, счета и цели, долги в
обе стороны и отчёт по группам и месяцам (фазы 1–4 плана; импорт писем
магазина — впереди). Вкладки: Платежи, Траты, Счета, Долги, Отчёт.

- **Будущие платежи не материализуются**: хранится план и правило повтора
  (`once|monthly|yearly|interval_months|interval_days` + `interval_n`), а
  вхождения до конца следующего месяца раскладываются на лету
  (`projectDues`, кап 40 вхождений на план — иначе ежедневные повторы дают
  сотни строк). Иначе пришлось бы переписывать тысячи будущих строк при
  каждом изменении суммы.
- **Оплата** (`POST /finance/plans/{id}/pay`): дата (можно задним числом),
  фактическая сумма и **periods** — «оплачено за N периодов вперёд», дата
  сдвигается на `N × интервал` (`AdvanceDue` с прижатием дня к концу месяца).
  Разовый план после оплаты выключается. `skip` двигает дату, записывая
  платёж с `skipped` и нулевой суммой — деньги не учитываются.
- **Примерные суммы** (`is_estimate`, ЖКХ): в списке со знаком «≈», при
  оплате подставляется среднее трёх последних платежей
  (`AverageFinancePayment`).
- **Валюты**: суммы хранятся в своей валюте, сводка приводится к базовой
  (`user_settings.finance_base_currency`) курсом на сервере — чтобы цифра в
  приложении и в уведомлении бота совпадала. **В истории платежа курс
  фиксируется** (`rate_to_base`): без этого прошлые месяцы пересчитывались бы
  при каждом изменении курса. Курсы — общий пакет `internal/rates`
  (выделен из `httpapi/converter.go`, когда потребовался второму потребителю).
- **Напоминания**: воркер `internal/financenotify` (тик 15 мин) шлёт в
  «утренний час» по часовому поясу пользователя (`finance_tz_off` приходит с
  клиента при открытии страницы). Дедуп — `notified_for`/`autopay_asked_for`
  по дате платежа. **Автоплатёж заранее не напоминает**, но на следующий день
  после даты один раз спрашивает «списалось?» — иначе в приложении копится
  неправда.
- **Долги** (`finance_debts` + `finance_debt_payments`): направление
  `owed_to_me|i_owe`, частичные возвраты, `paid`/`remaining` и статус
  **считаются по истории** (`recalcDebtStatus`), а не хранятся полем — иначе
  разъедутся; «простить остаток» = `forgiven`.
- **Сводка**: этот месяц / следующий / просрочено / нам должны + «из них
  спишется само» и «в среднем в месяц» (`monthlyCost`: годовое ÷ 12, раз в N
  месяцев ÷ N, интервал в днях × 30.44 ÷ N). Кнопка 👁 скрывает суммы
  (`finance_hide_amounts`) — для случая, когда на экран смотрит кто-то ещё.
- **Реестр денег ОДИН** — `finance_transactions`. Оплата планового платежа
  создаёт обычную транзакцию (`plan_id` + `payment_id`), иначе отчёт по
  категориям пришлось бы собирать из двух источников с разными правилами.
  `finance_payments` при этом остаётся: это журнал «за какую дату платежа
  заплатили», из него считаются среднее для примерных сумм и `periods`.
  Пропуск (`skip`) транзакцию не создаёт — деньги не потрачены.
- **Дерево категорий любой вложенности** (`finance_categories.parent_id`, как
  подгруппы Checker). Имя уникально в пределах родителя
  (`unique (user_id, coalesce(parent_id,0), lower(name))`), перенос в
  собственного потомка отбивается рекурсивным CTE. **Удаление узла не трогает
  деньги**: подкатегории, транзакции и планы поднимаются на родителя — уборка в
  справочнике не должна стирать траты. Фильтр «по категории» включает всё
  поддерево. `POST /finance/categories/seed` заводит типовой набор: пустой
  справочник отбивает желание записывать траты вообще. У плана категория —
  `category_id`, а текстовая `category` остаётся денормализованным именем
  (списки и вхождения показывают его без джойна).
- **Счета** (`finance_accounts`): остаток не хранится полем — стартовый плюс
  движения (то же правило, что у остатка долга). Перевод между счетами —
  транзакция `kind = transfer` с `to_account_id`, в отчёт не попадает: это
  перекладывание своих денег. Удалить счёт с движениями нельзя (409) — для
  этого есть архив, иначе `ON DELETE SET NULL` обезличил бы историю. Суммы в
  чужой валюте приводятся к валюте счёта **живым** курсом: остаток — величина
  «на сейчас», в отличие от отчёта.
- **Цели «отложено на»** (`finance_goals` + `finance_goal_moves`): конверт
  поверх счёта, а не отдельный кошелёк — деньги физически лежат на счёте,
  поэтому «отложил» его баланс не меняет. Накопленное считается по движениям
  (плюс — отложил, минус — снял).
- **Отчёт** (`GET /finance/stats?months=&from=&to=&category_id=`): расходы по
  месяцам и по группам, доля категории, сравнение с **прошлым периодом той же
  длины**, средний месяц (по месяцам с записями — пустые будущие занижали бы
  среднее). Считается в Go по «сырым» строкам периода: свёртка дерева и
  сравнение периодов в SQL пишутся, но читать и править такой запрос потом
  невозможно, а объёмы личных финансов ничтожны. Сумма приводится курсом,
  зафиксированным в записи, и только если базовая валюта с тех пор не менялась
  (иначе — живым курсом): прошлые месяцы не должны «плыть».
- **Таблицы**: `finance_plans`, `finance_payments`, `finance_debts`,
  `finance_debt_payments` + 4 колонки в `user_settings` — миграция 0076;
  `finance_categories`, `finance_accounts`, `finance_transactions`,
  `finance_goals`, `finance_goal_moves` + `finance_plans.category_id/account_id`
  — миграция 0085 (текстовые категории планов перенесены в дерево по названиям).
  Деньги — `NUMERIC(14,2)`.
- **Разбивка траты по категориям** (`finance_tx_splits`, v2.72). Трата остаётся
  ОДНОЙ строкой (поход в магазин — одна трата), но делится на доли. Отчёт берёт
  их `LEFT JOIN`-ом: у траты с разбивкой строка на каждую долю, у остальных —
  одна строка с суммой целиком. Поэтому **круговая диаграмма и отчёт по
  категориям считаются одним механизмом**, а месячные итоги не меняются. Фильтр
  ленты по категории тоже смотрит в доли — иначе переход из отчёта в ленту
  терял бы разложенные чеки.
  - ⚠️ **Доли обязаны сходиться с суммой траты.** Они масштабируются (сумма
    позиций не равна subtotal) и округляются, поэтому остаток отдаётся самой
    крупной доле (`reconcile`). Разошедшийся отчёт хуже отсутствующего.
  - Доля с `category_id = NULL` — «Не разобрано»: видимый кусок диаграммы, а не
    молчаливое «Прочее».
- **Группы товаров** (v2.72). Слои: память решений (`finance_item_rules`, ключ
  = нормализованное название + магазин) → встроенный словарь подстрок
  (`internal/receipts/groups.go`) → «Не разобрано». Ручное решение словарём не
  перетирается. Соответствие встроенных групп категориям пользователя лежит в
  `finance_item_groups`: деревья у всех разные, по названию угадывать нельзя;
  `SeedItemGroups` переиспользует существующую категорию с тем же именем.
  Решение применяется по **всем** чекам (`ApplyItemRuleEverywhere`) с
  пересборкой долей — иначе разметка чинила бы только будущее.
  - ⚠️ **Любая правка соответствия групп категориям обязана вызывать
    `ClassifyAll`**: без этого смена привязки не трогает уже разобранные чеки и
    настройка выглядит сломанной (переставили группу — отчёт прежний).
  - ⚠️ **Несколько групп в одной категории убивают всю затею**: доли считаются
    верно, но сливаются в один сектор диаграммы. Интерфейс предупреждает об
    этом и предлагает `seed` с `reset: true` — он перепривязывает все группы к
    своим категориям и перебирает чеки. Обычный `seed` заполняет только
    недостающие коды.
  - Ручная разметка указывает на КАТЕГОРИЮ, а не на группу, поэтому смена
    привязки группы её не двигает — это осознанно.
  - **Свои словарные правила** (`finance_word_rules`, v2.73) проверяются ДО
    встроенного словаря — ими же его и переопределяют. Полный порядок:
    ручная разметка → свои слова → встроенный словарь → «Не разобрано».
    Отдельной сущности «группа» у пользователя нет: своя группа = категория
    плюс слова к ней.
  - ⚠️ **Любое изменение правил обязано вызывать `ClassifyAll`** — как и смена
    привязки групп.
- **Форматы даты доставки** у магазина менялись: в 2024-м
  `10/13/2024 2:24:54 PM`, сейчас `2026-08-04 17:53`. Непонятая дата = трата
  уезжает в сегодняшний день, то есть покупка 2024 года попадает в текущий
  месяц отчёта. Разбор пробует список шаблонов (`dateLayouts`); в шаблонах
  однозначные `1/2/2006` — с ними Go разбирает и `10/13/2024`, а с
  `01/02/2006` только двузначные.
- **Перечитывание чека** (`POST /mail/messages/{id}/parse {"refresh":true}`) —
  когда разбор поумнел: обновляет чек и подтягивает за ним дату и сумму
  созданной траты. Без него исправить старые чеки можно было бы только руками
  в базе.
- **AI-подсказки групп** — поверх `ai_tasks`/`ai_runs`: строгий промпт, ответ
  парсится от первой `[` до последней `]` (модели обрамляют JSON пояснениями и
  ```-блоками), неизвестные группы отбрасываются. **Ничего не применяется без
  человека.**
- **История цен** — цена за единицу (`amount/qty`): количество в чеках плавает
  (вес, штуки). Нормализация названия НЕ отбрасывает объём: «0.5l» и «0.33l» —
  разные товары с разной ценой.
- **API фаз 3–4**: `GET /finance/refs` (категории + счета с остатками + цели +
  валюты одним запросом — три похода за справочниками при каждом открытии формы
  заметны на мобильном), `GET|POST /finance/transactions`,
  `PUT|DELETE /finance/transactions/{id}`, `GET|POST /finance/categories`,
  `POST /finance/categories/seed`, `PUT|DELETE /finance/categories/{id}`,
  `POST /finance/categories/{id}/archive`, `GET|POST /finance/accounts`,
  `PUT|DELETE /finance/accounts/{id}`, `POST /finance/accounts/{id}/archive`,
  `GET|POST /finance/goals`, `PUT|DELETE /finance/goals/{id}`,
  `GET|POST /finance/goals/{id}/moves`,
  `DELETE /finance/goals/{id}/moves/{move_id}`, `GET /finance/stats`.
- **API групп товаров** (v2.72): `GET /finance/item-groups`,
  `POST /finance/item-groups/seed`, `PUT /finance/item-groups/{code}`,
  `GET /finance/items/unclassified`, `POST /finance/items/assign`,
  `GET|DELETE /finance/items/rules[/{id}]`, `GET /finance/items/top`,
  `GET /finance/items/prices`, `POST /finance/items/suggest`,
  `GET /finance/items/suggest/{run_id}`,
  `POST /finance/receipts/{id}/classify`,
  `GET|PUT /finance/transactions/{id}/splits`.

### 🧠 Тесты (`/tests`) — v2.63, personal
Карточки вопросов с вариантами ответов и личным прогрессом. Первая колода —
официальные экзаменационные вопросы по ПДД Армении (1032 вопроса, 669
картинок, комплект дорожной полиции от 25.12.2025).

- **Разделение данных**: контент (`test_decks` / `test_groups` /
  `test_questions`) общий для всех, прогресс (`test_progress`) и прогоны
  (`test_sessions` / `test_session_items`) — личные. Миграция 0071.
- **Пулы прогона** (`scope`): `unpassed` (основной сценарий «продолжить»),
  `wrong` (работа над ошибками), `group` (по теме), `all`. Пул выбирается и
  **перемешивается на сервере** при создании прогона, порядок сохраняется в
  `test_session_items` — перезагрузка страницы не тасует колоду.
- **Когда вопрос пройден**: после N верных ответов подряд
  (`user_settings.tests_pass_streak`, 1–5, по умолчанию 1 — настраивается
  шестерёнкой страницы). Ошибка сбрасывает серию и возвращает вопрос в пул.
- **Экзамен**: параметры в колоде (`exam_size` 20, `exam_minutes` 30,
  `exam_allowed_mistakes` 2). Дедлайн — `expires_at`, вердикт `passed`
  считается при завершении (в т.ч. досрочном и по таймауту), верные ответы
  показываются только в разборе.
- **Правильный ответ не утекает**: `correct_idx` отсутствует и в списке
  вопросов, и в выдаче текущего вопроса — приходит ТОЛЬКО в ответе на
  `POST /answer` (и в `/review` завершённого прогона). Иначе учебный режим
  обесценивается парой кликов в девтулзах.
- **Сброс**: мягкий (снимает отметки «пройден», статистика ответов остаётся)
  и жёсткий (`hard: true` — удаляет прогресс целиком).
- **API**: `GET /tests/decks` (со сводкой и активным прогоном),
  `GET /tests/decks/{id}/groups`, `POST /tests/decks/{id}/reset`,
  `POST /tests/sessions`, `GET|POST /tests/sessions/{id}[/answer|/finish]`,
  `GET /tests/sessions/{id}/review`, `GET|PUT /tests/settings`.
- **Импорт колоды** — админский `POST /admin/tests/import` (multipart:
  `deck` JSON + `images` zip), идемпотентный по `(slug, num)`: переимпорт
  обновляет тексты и ответы, НЕ сбрасывая прогресс (id вопросов сохраняются).
  Картинки распаковываются в `DATA_DIR/tests`, раздаются из `/uploads/tests/`
  (публично, как остальные загрузки). Колода заливается **не миграцией**:
  1032 вопроса в `.sql` нечитаемы и неисправимы.
- **Сборка и сверка данных**: `habits/tools/pdd-import/` — `build_bundle.py`
  качает вопросы и картинки, `verify.py` сверяет их с официальными PDF
  (`roadpolice.am/exam/ru_group_{1..10}.pdf`) постранично по мультимножеству
  ответов; без сверки пакет не собирается. Подробности, включая найденный
  дефект русского PDF (у вопроса 854 потеряна строка варианта — восстановлена
  по английской версии), — в README рядом.

Инструкции по каждой странице (раскрывающиеся секции) + форма «Написать

(фильтр по `pageAllowed`); недоступные скрыты.

### ⚙️ Settings (`/settings`) — общие настройки, v2.80
Начиная с **v2.45** страница содержит только общие настройки; настройки
конкретных страниц вынесены в шестерёнку в шапке (см. ниже).
- **«Какие страницы мне видны»** (v2.80, `components/VisiblePages.vue`) —
  галочка у каждой доступной страницы; снятая убирает страницу из меню и с
  плиток главной. Это НЕ доступ: доступы выдаёт админ (`page_access`), а
  здесь показаны только те страницы, что пользователю и так доступны, и
  скрытая продолжает открываться по прямой ссылке и находиться поиском —
  смысл в том, чтобы убрать с глаз лишнее, а не запретить. «Настроек» в
  списке нет: спрятав их, пользователь потерял бы путь обратно (на сервере
  это же ограничение — `hidablePages`). Кнопка «Показать все (N скрыто)»
  шлёт ОДИН запрос со списком целиком: по странице за раз получалась бы
  пачка запросов, и ответ отставшего возвращал бы в интерфейс промежуточное
  состояние. Хранение — `user_settings.hidden_pages` (миграция 0109),
  `PUT /me/pages/hidden` заменяет список целиком.
- **Оформление** (сворачивающийся блок, `SettingsView.appearanceOpen`) — три
  подраздела:
  - **Тема интерфейса** (поднята наверх): авто (из Telegram) / светлая / тёмная.
  - **Фон приложения**: загрузка картинки (до 5 МБ, тип проверяется по
    сигнатуре), галерея загруженных, URL, размещение
    (заполнить/замостить/центр), **размытие 0–30 px**, **темнее/светлее ±70 %**.
    **Цвет текста** и **цвет фона** — отдельно для тёмной и светлой темы
    (color-picker со сбросом; хранятся на сервере, применяются на лету при
    смене темы) — полезно, когда свой фон сливается со стандартным текстом.
    Кнопка **«🤖 Из чата бота»**: отправьте картинку боту сообщением — воркер
    (`internal/tgphotos`, длинный getUpdates) скачает её и положит в галерею,
    бот ответит подтверждением; открытая модалка сама подхватывает новую
    картинку (поллинг галереи раз в 4 с).
    Фон хранится на сервере, кэшируется локально (применяется мгновенно).
    На iOS рисуется отдельным `position: fixed`-слоем —
    `background-attachment: fixed` там сломан.
  - **Карточки — «стекло»** (v2.19): непрозрачность 20–100 % (100 — сплошные,
    как раньше) и размытие фона под карточкой 0–30 px (frosted glass). Хранится
    в `user_settings.card_opacity/card_blur`. Реализация: `--card-color` собран
    из `rgba(var(--card-rgb), var(--card-alpha))`, JS ставит `--card-alpha`/
    `--card-blur` и атрибут `data-card-glass` на `<html>`; `backdrop-filter`
    включается на карточках — уникальные классы перечислены глобально в
    `theme.css`, неоднозначные (`.section`/`.entry`/`.category`/`.group`/
    `.project`/`.pass-item`) размываются локальным правилом в scoped-стилях
    своих компонентов (чтобы не задеть одноимённые не-карточки).
- **Модалки** (v2.34): глобальная `.modal-content` (`theme.css`) ограничена по
  высоте (`max-height: 100dvh − 24px`, фолбэк `vh`) с `overflow-y: auto` —
  высокие окна настроек прокручиваются, а не уходят за экран.
- **О приложении**: версия, пользователь.

### 🎨 Оформление 2.0 (v2.67)
⚠️ **Родные элементы формы и `color-scheme`.** `applyTokens` ставит на `<html>`
не только токены, но и `color-scheme` — по ЯРКОСТИ фона темы, а не по её виду:
своя тема бывает тёмной, хотя заведена как светлая. Без этого браузер рисует
выпадающий список `<select>`, полосы прокрутки и автозаполнение светлой
палитрой. То же правило продублировано в `theme.css` на `:root[data-theme]` —
чтобы не мигало до применения токенов из JS.
⚠️ **Фон полей ввода — только непрозрачный** (`var(--bg-secondary)`, никогда
`var(--card-color)`). Полупрозрачный выглядит нормально в обычном браузере, но
вебвью Telegram на десктопе подкладывает под родной элемент свой светлый фон, и
по тёмной теме получается белое поле со светлым текстом.
Темы, своя тема, рамки и фоны. Настройки → «Оформление» (блок помнит, свёрнут
ли он: `ui_collapsed.settings`, id 1).

- **Токены вместо колонок**: тема — набор значений (`bg`, `text`,
  `text_secondary`, `accent`, `card_rgb`, `card_alpha`, `card_blur`,
  `cell_bg`, `hover_bg`, `border_card_*`, `border_btn_*`), которые
  выставляются CSS-переменными на `<html>` (`shared/themes.ts`). Раньше каждая
  новая настройка означала колонку в `user_settings`; их было восемь при двух
  темах. Теперь оформление — **один JSONB на режим входа**: `appearance` и

  `text_color_*`/`bg_color_*`/`card_*` — вид ни у кого не изменился).
- **8 встроенных тем** в коде фронтенда (в базе только id): тёмные Ночь,
  Графит, Индиго, Контраст; светлые День, Бумага, Небо, Контраст. «Ночь» и
  «День» повторяют прежний вид приложения.
- **Своя тема**: правка любого цвета копирует текущую тему в черновик
  (`state.draft`) и переключает на него — встроенную тему на месте не меняем,
  иначе к ней не вернуться. Черновик живёт на сервере.
- **Тема = весь вид, включая фон** (v2.68): при сохранении сервер снимает
  текущий фон и **копирует файл** (`theme_<rand>` в каталоге фонов, вместе с
  превью) — удаление картинки из своей коллекции сохранённую тему не ломает.

- **Пополнение галереи из своих фонов** (v2.68): `POST
  /admin/gallery/images/from-background {image_id}` копирует файл (и превью)
  из каталога фонов в галерею — админ не выкачивает и не загружает заново.
- **«Как в системе» — пара тем** (`auto_light` + `auto_dark`), а не просто
  светлая/тёмная: иначе выбор сбрасывался бы на дефолтные.
- **Рамки** карточек и кнопок — `box-shadow: inset`, а НЕ `border`: тень не
  влияет на размеры вообще, поэтому включение рамки не разъезжает вёрстку.

- **Генератор**: один акцентный цвет → согласованный набор токенов

- **Фоны**: вложенные папки (`background_folders`, сворачивание на папке,

## 2. Авторизация и роли

- Каждый запрос к `/api/v1/*` несёт `Authorization: tma <initData>` **или**
  `Authorization: Bearer <токен доступа>` (v2.59 — вход вне Telegram);
  подпись initData проверяется HMAC-SHA256 по алгоритму Telegram
  (`internal/auth/telegram.go`), initData старше 24 ч отклоняется.
- Раз в 5 минут на пользователя обновляется `last_seen_at` и фиксируется
  уникальная связка IP (X-Forwarded-For от Caddy) + устройство
  (короткая форма из User-Agent: «iPhone · Telegram»).
- **Роли**: ID админов — в конфиге сервера (`ADMIN_IDS`, `/opt/habits/.env`).
  Админ видит в Settings список пользователей (последний заход, устройство,
  IP), карточку пользователя (первый/последний заход, все связки IP+устройство
  с датой регистрации, счётчики данных по страницам — без самих данных)
  и может банить/разбанивать. Забаненный получает 403 на весь API
  (действует немедленно). Локальная разработка: `DEV_AUTH_BYPASS=true` +
  `Authorization: tma dev`.


### Токены доступа (v2.59)
Долгоживущий персональный секрет для входа **вне Telegram** (веб-версия,
расширение браузера; та же таблица пригодится MCP-серверу). initData живёт
24 часа и требует мини-апп, поэтому нужен отдельный механизм.

- Таблица `access_tokens` (миграция 0064): `token_hash` (sha256, UNIQUE) —
  **сам токен не хранится**; `prefix` (первые символы) для опознания в списке,
  `name`, `expires_at`, `last_used_at`, `last_device`, `revoked_at`.
  Формат токена: `hbt_` + 48 hex. Лимит 10 активных на пользователя.
- `auth.Middleware.authenticateToken`: ищет владельца по хэшу (активный и не
  истёкший), берёт `username`/`first_name` из БД — иначе `TouchUser` затёр бы
  их пустыми; `last_used_at` пишется не чаще раза в 5 минут (`sync.Map`).
- **Границы токен-сессии** (`isTokenForbiddenPath`, проверка прямо в `Wrap`):
  `/api/v1/admin/*` и `/api/v1/settings/tokens*` — 403. Утёкший токен не даёт
  ни админ-полномочий, ни выпуска новых токенов.
- **Две разные проверки админа**, не путать:
  - `IsAdmin(userID)` — «человек админ»: видимость СВОИХ personal-страниц
    (`access.go`), признак в карточке пользователя. От способа входа не зависит.
  - `IsAdminSession(ctx)` — «у сессии есть админ-полномочия» = не токен-сессия
    И админ: `/me` (`is_admin`), `adminOnly`, `tech_notes` в списке релизов.
- API: `GET/POST /settings/tokens`, `DELETE /settings/tokens/{id}` (только из
  Telegram). Сам токен возвращается **один раз** — при создании.
- UI: сворачиваемый блок «Токены доступа» в Settings.
- **Защита от подбора** (v2.62, `internal/auth/brute.go`): счётчик неудачных
  Bearer-попыток по IP — окно 5 мин, порог 10, блокировка 15 мин (предохранитель
  на 10000 адресов). Заблокированный IP не доходит до БД, `Wrap` отвечает
  **429 `too_many_attempts`**, включение блокировки пишется в лог WARN; удачный
  вход сбрасывает счётчик. Сам токен — 192 бита, перебор нереален; лимитер
  снимает нагрузку на БД и делает попытки заметными.

### Веб-версия и расширение (v2.60)
Одна сборка обслуживает Telegram, браузер и расширение — режим определяется в
рантайме (`shared/auth.ts`):

| `authMode` | Когда | Заголовок |
|---|---|---|
| `tma` | есть `initData` (или `npm run dev`) | `tma <initData>` |
| `token` | токен в `localStorage` | `Bearer <токен>` |
| `none` | ни того, ни другого | — показывается `TokenGate` |

- `client.ts`: `authHeader()` отдаёт `Bearer`, когда `initData` пуст; на **401**
  вызывает `onTokenRejected()` — токен сбрасывается, экран входа появляется сам
  (отозвали/истёк).
- `components/TokenGate.vue`: ввод токена с проверкой через `GET /me`.
- В токен-режиме скрыты «Оформление» и блок токенов (`v-if="!isTokenMode"`);
  админка и Релизы прячутся сами — `/me` отдаёт `is_admin: false` (см. выше).
- **Тема — на сервере** (v2.61, миграция 0067): `user_settings.theme`
  (основная, из Telegram) + `web_theme`/`web_bg_off` — переопределения
  **только** для токен-сессий. Раньше тема жила лишь в `localStorage`, а у
  extension-origin оно партиционировано — отсюда «в браузере всегда светлая».
  `GET/PUT /settings/appearance`; **PUT выбирает колонки по виду сессии**
  (`tma` → `theme`, `token` → `web_*`), поэтому браузер не может изменить тему
  мини-приложения. `shared/appearance.ts` применяет `effectiveTheme` и
  кэширует в localStorage (первый кадр без мигания); `bgHidden()` гасит фон.
- **Расширение** (v2.62 — раздаётся с домена): исходники в
  `backend/internal/extension/files`, вшиты `go:embed`; zip собирается в
  памяти при первом запросе и кэшируется, `{{APP_URL}}` в `popup.html` и в
  манифесте подставляется из `PUBLIC_URL`. Скачивание публичное, вне
  tma-авторизации (внутри только клиент), ссылки в Settings → «Токены
  доступа». Отдельный файл на браузер: копировать манифест руками не нужно.
- **Подпись Firefox** (v2.64): Firefox снимает неподписанное дополнение при
  перезапуске, поэтому для него раздаётся **подписанный Mozilla `.xpi`** —
  `GET /ext/habits-firefox.xpi` (тип `application/x-xpinstall`), плюс
  `GET /ext/updates.json` для самообновления (`update_url` внутри манифеста).
  Канал подписи — **unlisted**: файл подписан, но в каталоге AMO не
  публикуется, проверка автоматическая. Подпись покрывает байты, поэтому
  `.xpi` — единственный бинарник в репозитории
  (`files/signed/habits-firefox.xpi`) и адрес приложения зашит в него в момент
  подписи; собрать на лету, как zip, нельзя. Скрипт `sign-firefox.sh` берёт
  ключи из `~/.config/habits-amo.env` (вне репозитория). ⚠️ Новая подпись
  требует поднять `version` в `manifest.firefox.json` — AMO не примет ту же
  версию повторно; версия и id для `updates.json` читаются из самого `.xpi`.
  `/ext/habits-firefox.zip` остаётся для разработки (временная установка).

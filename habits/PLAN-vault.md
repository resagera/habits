# Сейф (`/vault`) — план

Отдельная страница-хранилище: файлы шифруются в браузере паролем папки, на
сервере лежат только двоичные шифроданные. Расшифровка и просмотр — тоже в
браузере. План согласован 2026-09-03; здесь зафиксированы принятые решения,
чтобы не переигрывать их по ходу.

Предыстория и разбор осуществимости — в `BACKLOG.md`, раздел «Шифрование
картинок паролем на клиенте».

## Принятые решения

| Вопрос | Решение |
|---|---|
| PDF в вебвью Telegram | **Без pdf.js.** Кнопка «Открыть в браузере» + скачивание; в браузере пароль вводится заново. |
| Большие файлы | **Чанковое шифрование сразу**, лимит VIP на файл снижен. |
| Удаление | **Сразу, без корзины**, подтверждение вторым тапом. |
| Ключ восстановления | **Не делаем.** Забыл пароль — файлы потеряны, предупреждаем прямо. |
| Квота | Считается **только владельцу**; файл удалил владелец — он пропадает у всех, кому расшарен (доступ, а не копия). |
| Превью картинок | **Опция при создании папки**, потом не меняется: сделанные превью нельзя достроить задним числом, сервер их построить не может. |
| Временная ссылка | **Только с паролем** (вариант А): открыл ссылку — введи пароль. Ключа в URL нет. **Одна ссылка = один файл.** |
| Скрытие подпапок | **Косметическое**: сервер по-прежнему знает имена, у галочки это написано прямым текстом. |
| Усиление KDF (Argon2id) | **На потом**, отдельным заходом — см. «Что отложено». |

Из предложенных дополнений делаем: подсказку к паролю, чанки, полосу квоты с
проверкой до записи на диск, массовые операции, загрузку перетаскиванием /
из буфера / с камеры, автозамок при уходе со вкладки, честный текст в
уведомлении о шаринге. **Не делаем**: ключ восстановления и публичную ссылку
с ключом во фрагменте URL.

## Криптосхема

```
пароль папки ──PBKDF2-SHA256(salt, 310k)──▶ KEK
                                             │ разворачивает
                                             ▼
                                        FK (ключ папки)
файл: содержимое ──AES-GCM(CK) чанками──▶ шифроблоб на диске
      CK ──AES-GCM(FK)──▶ key_env
      {имя, тип, размер, ширина/высота} ──AES-GCM(FK)──▶ meta_env
```

- **Ключ содержимого на каждый файл (CK)**, обёрнутый ключом папки (FK).
  Смена пароля папки = перезапись одной обёртки FK, а не всех файлов;
  перенос файла в другую папку = переворот 32 байт, без перезаливки.
- **У каждой папки свой salt и своя обёртка FK**, даже при одинаковом пароле:
  любая папка самодостаточна, расшаренную подпапку получатель открывает, не
  имея доступа к родителю.
- **Проверочный блоб не нужен**: GCM-тег на обёртке FK и есть проверка пароля.
- Имена файлов и типы зашифрованы (`meta_env`), имя папки — открыто: иначе
  нечего показать до ввода пароля и нечего написать в уведомлении о шаринге.
- Формат блоба: заголовок `HVLT` + версия + размер чанка + база IV, затем
  чанки по 4 МБ, каждый — AES-GCM с IV = база ‖ счётчик.

## Замок

- Ключи в памяти страницы, `Map<folderId, CryptoKey>`; **TTL 60 секунд**,
  сбрасывается при каждом действии.
- 🔒 на папке — запереть сразу; в шапке — «запереть всё».
- Автозамок при уходе со вкладки.
- Ключ хранится как **неизвлекаемый CryptoKey**; строка пароля живёт столько
  же и нужна только для автооткрытия соседних папок с тем же паролем.
- При блокировке отзываются blob-URL и чистятся `src` — иначе расшифрованное
  остаётся на экране после «замка».

## Данные

```
vault_folders(id, user_id, parent_id, name, hint, thumbs,
              kdf_salt, kdf_iter, wrapped_key, wrap_iv, position, …)
vault_files(id, user_id, folder_id, blob_name, thumb_name,
            size_bytes, plain_size, key_env, meta_env, chunk_size, …)
vault_shares(kind, target_id, user_id)      -- kind: folder | file
user_type_limits += vault_file_mb, vault_total_mb
```

Лимиты по умолчанию (правятся в админке):

| Тип | Файл | Всего |
|---|---|---|
| regular | 3 МБ | 10 МБ |
| payed1 | 10 МБ | 300 МБ |
| payed2 | 50 МБ | 1 ГБ |
| vip | 50 МБ | 1 ГБ |

## Загрузка чанками

`POST /vault/uploads` (init: папка, заявленный размер, размер чанка) →
`POST /vault/uploads/{id}/chunk?i=N` (сырые байты) → `POST /vault/uploads/{id}/finish`
(конверты, превью). Квота проверяется на init по заявленному размеру и ещё раз
на finish по фактическому — до появления строки в базе. Брошенные загрузки
подчищаются по времени.

Одним потоковым запросом сделать нельзя: `fetch` с `ReadableStream` в теле
требует HTTP/2 и не работает в Safari/iOS.

## Просмотр

| Тип | Как |
|---|---|
| jpeg/png/webp/gif/avif | `<img src=blob>` |
| svg | только через `<img>`, в DOM не вставляем (иначе выполнятся скрипты внутри) |
| txt/md/csv/json/код | `<pre>` с потолком показа |
| аудио, видео | `<audio>` / `<video>` с blob-URL |
| pdf | `<iframe>` (работает в браузере), в Telegram — «Открыть в браузере» и скачивание |
| прочее | скачивание |

Скачивание внутри вебвью Telegram ненадёжно (`<a download>` с blob), а
нативный `downloadFile` требует публичный URL — для шифрованного файла его
быть не может. Значит внутри Telegram основной сценарий — просмотр, а
скачивание — в веб-версии и расширении.

## Временные ссылки на файл (вариант А)

Одна ссылка ведёт ровно на **один файл**; папку ссылкой не отдать.

- При создании ссылки браузер разворачивает ключ содержимого (CK) ключом
  папки и **заворачивает его заново в отдельный конверт** под паролем ссылки
  (свои соль и итерации). Имя и тип файла шифруются тем же ключом ссылки —
  получателю нечем расшифровать `meta_env` папки, он ключа папки не знает.
- **Ключ папки в ссылку не попадает.** Утёкшая ссылка компрометирует один
  файл, а не всю папку, и только вместе с паролем.
- Пароль ссылки задаёт владелец при создании — это может быть пароль папки,
  но лучше отдельный: его и передают получателю другим каналом.
- В базе лежит **только SHA-256 токена**: утечка базы не даёт рабочих ссылок.
  Токен — 32 случайных байта в base64url (43 символа) в пути.
- Срок: 1 час по умолчанию, на выбор 15 минут / 1 час / сутки / неделя.
  Плюс необязательный лимит открытий и кнопка «отозвать».
- Просроченная, отозванная, исчерпанная ссылка и удалённый файл отвечают
  **одинаковым 404** — по ответу нельзя понять, существовал ли файл.
- Страница `/l/{token}` открывается **без авторизации**, как `/read/{token}`
  у статей. Публичные страницы рисуются без меню и шапки и не дёргают
  закрытые ручки (сейчас `TokenGate` закрыл бы и `/read` в чистом браузере —
  чиним заодно).

## Срок жизни файла

- У файла — `expires_at`, у папки — «удалять файлы через N дней» (по
  умолчанию 0 = никогда), проставляется загружаемым в неё файлам.
- Уборщик в бэкенде раз в час сносит просроченные файлы (строка, блоб,
  превью), просроченные ссылки и старые записи журнала.
- Место освобождается сразу, как при обычном удалении: корзины нет.

## Журнал доступа

- `vault_access_log(file_id, user_id, via, at)`: `via` — `share` (открыл тот,
  кому расшарено) или `link` (открыли по временной ссылке, `user_id` пуст).
- Пишется при выдаче блоба, если смотрит **не владелец**. Владельцу показываем
  последние записи в карточке файла.
- Сервер видит только факт обращения — не содержимое.

## Скрытие подпапок

Флаг `hide_children` на папке: пока папка не открыта паролем, вложенные не
показываются. **Это косметика, а не крипта** — имена папок в базе открыты, и у
галочки так и написано. Настоящее скрытие потребовало бы шифровать имя
подпапки ключом родителя; тогда в уведомлении о шаринге назвать её было бы
нечем.

## Просмотр: docx и zip (бывший этап 3)

- **docx** — это zip с `word/document.xml`. Разбираем `fflate` + `DOMParser`,
  собираем абзацы, заголовки, жирный/курсив и списки. Тяжёлую библиотеку
  (mammoth ~1 МБ) не тянем: полная верстань здесь и не нужна.
- **zip** — список содержимого с размерами; отдельный файл внутри можно
  открыть тем же просмотрщиком.
- **Выгрузка папки архивом** — расшифровка всех файлов в браузере и сборка
  zip без сжатия (содержимое уже несжимаемо). Внутри Telegram скачивание
  ненадёжно — предупреждаем и оставляем сценарий для браузера.

## Что отложено

- **Argon2id вместо PBKDF2** (WASM, memory-hard): при том же ожидании ~1 с
  поднимает цену перебора примерно в 100 раз. Поле `kdf` делаем полиморфным,
  старые папки продолжают открываться, переезд — при смене пароля.
- Перенос папок между родителями, биометрия/passkey для быстрого открытия,
  подписанный манифест папки против подмены блобов сервером.

## Этапы

- **Этап 1 (ядро)**: страница, папки и подпапки, пароль на папку с подсказкой,
  замок с таймером, загрузка чанками, просмотр картинок/текста/аудио/видео,
  PDF через браузер, квоты и поля в админке, массовые операции.
- **Этап 2 (шаринг)**: доступ к файлу и к папке, уведомление бота с явным
  «пароль отправьте отдельно», чужие папки в списке.
- **Этап 3 (сделан в 2.84)**: страница, папки, замок, чанки, просмотр, шаринг.
- **Этап 4 (2.85)**:
  - заметность: явный выбор карточек, «выделить всё», действия над одним
    файлом (переименовать, заметка, копировать, ссылка, срок, журнал, удалить);
  - поиск по именам внутри открытой папки;
  - копирование файла в другую папку без перезаливки (переворот ключа);
  - временные ссылки (вариант А);
  - косметическое скрытие подпапок;
  - полноэкранный просмотр со свайпом и зумом;
  - заметка к файлу (в уже шифруемых метаданных);
  - самоуничтожение по сроку;
  - журнал доступа к расшаренному;
  - возобновление прерванной загрузки;
  - docx/zip-просмотр и zip-выгрузка папки.

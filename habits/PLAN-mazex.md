# Лабиринты-Экстра (`mazex`) — план реализации и деплоя

Файл для отдельной сессии: здесь всё, что нужно знать про новую игру, её
архитектуру, контракты и выкладку. Самой игры ещё нет — есть решение, как её
делать. Читать вместе со `skill habits` (правила репозитория и порядок релиза)
и разделом «🎮 Игры» в `DOCS.md` (как устроены уже готовые игры).

## 1. Замысел

«Лабиринты-Экстра» — отдельная игра на странице «Игры», сложнее обычного
лабиринта. Отличие от остальных игр **не в правилах, а в том, где живёт
логика**: партию ведёт отдельный сервис, а не браузер.

Разделение ответственности:

```
  браузер (мини-апп)        игровой сервис            основной бэкенд
  ─────────────────         ──────────────            ───────────────
  рисует поле               ведёт партию              БД: пользователи,
  шлёт ввод                 считает правила           рекорды, настройки,
  показывает счёт           держит состояние          картинки, журнал партий
         │                   в памяти                        │
         └──── WS/HTTP ─────────┘  └──── внутренний HTTP ─────┘
```

**Правило, которое определяет всё остальное: у игрового сервиса нет своей базы
и своих файлов.** Всё, что должно пережить перезапуск контейнера, уходит в
основной бэкенд. Сервис — это только «общение»: с клиентом по вебсокету и с
ядром по внутреннему HTTP. Поэтому его можно перезапускать, катить отдельно и
даже потерять — пропадут только незаконченные партии.

Почему так, а не «ещё одна игра в браузере»: в браузере нельзя доверять ни
счёту, ни таймеру (рекорд ставится правкой переменной в девтулзах), и нельзя
сделать общую партию на двоих. Сервис закрывает оба вопроса.

## 2. Модель данных (всё в основной БД)

### Переиспользуем как есть

| Таблица | Что даёт | Что писать |
|---|---|---|
| `game_scores` | рекорды и число партий | код игры `mazex`, варианты через двоеточие: `mazex:normal`, `mazex:huge` |
| `game_backgrounds` | картинки под игру | слот `game` (фон), при нужде `walls` |
| `game_textures` | плитки стен от админа | `game = 'mazex'` или общие с `maze` |

Направление «лучше» и список слотов задаются одной строкой в `gameRules`
(`backend/internal/httpapi/games.go`). Рекорды и картинки заводить заново **не
нужно** — вся механика уже работает.

### Новое: журнал партий

Нужен, потому что «Экстра» считает статистику на сервере, а `game_scores`
хранит только лучший результат.

```sql
CREATE TABLE mazex_runs (
  id           BIGSERIAL PRIMARY KEY,
  user_id      BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  started_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  finished_at  TIMESTAMPTZ,
  -- лабиринт воспроизводится по seed: хранить сетку незачем
  seed         BIGINT  NOT NULL,
  cols         INTEGER NOT NULL,
  rows         INTEGER NOT NULL,
  variant      TEXT    NOT NULL,            -- normal | big | huge | режим «Экстры»
  outcome      TEXT    NOT NULL DEFAULT 'quit',  -- win | quit | timeout
  duration_ms  INTEGER NOT NULL DEFAULT 0,
  cells        INTEGER NOT NULL DEFAULT 0,  -- пройдено клеток
  shortest     INTEGER NOT NULL DEFAULT 0,  -- кратчайший путь, для оценки оптимальности
  extra        JSONB                        -- что добавит сама игра: ключи, монеты, жизни
);

CREATE INDEX mazex_runs_user_idx ON mazex_runs (user_id, started_at DESC);
```

Партию восстанавливать после перезапуска сервиса **не планируем**: в `extra`
складываем только итог. Если позже понадобится «продолжить на другом
устройстве» — отдельная таблица `mazex_state (user_id PK, run_id, state JSONB,
updated_at)`, снимок раз в несколько секунд.

### Кто ходит в эти таблицы

Только основной бэкенд. Игровой сервис их не знает и строки `DATABASE_URL` не
получает — это сознательное ограничение, иначе через полгода у нас две модели
данных и две очереди миграций на одну базу.

### Токен сервиса

По образцу машинных агентов (`file_machines`, `ai_machines`):

```sql
CREATE TABLE game_services (
  id           BIGSERIAL PRIMARY KEY,
  name         TEXT NOT NULL,
  token        TEXT NOT NULL UNIQUE,
  last_seen_at TIMESTAMPTZ,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

Строка с токеном вставляется **прямо в прод-БД**, не миграцией; сам токен
лежит в `~/.config/habits-mazex.token` на дев-машине и в `.env` на сервере.
В репозиторий не попадает (правило проекта, см. skill).

## 3. Контракт «сервис ↔ ядро» (внутренний HTTP)

Все ручки под `/api/v1/internal/mazex/*`, авторизация
`Authorization: Bearer <service token>`, проверка — по `game_services.token`.
Middleware `pageGuard` на них не распространяется: это не пользовательский
трафик.

| Метод | Ручка | Зачем |
|---|---|---|
| `POST` | `/session/resolve` | по одноразовому билету вернуть, кто это: `{user_id, name, variant_records, backgrounds, textures}` |
| `POST` | `/runs` | начало партии: `{user_id, seed, cols, rows, variant}` → `{run_id}` |
| `PATCH` | `/runs/{id}` | итог: `{outcome, duration_ms, cells, shortest, extra}`; ядро тут же обновляет `game_scores` по правилам `gameRules` |
| `GET` | `/stats/{user_id}` | рекорды и последние партии для экрана итогов |

Рекорд обновляет **ядро**, а не сервис: там уже лежит сравнение
«больше/меньше» в одном `INSERT … ON CONFLICT`, и дублировать его нельзя.

## 4. Контракт «клиент ↔ сервис»

Адрес сервиса и билет клиент берёт у ядра, а не зашивает в себе:

```
GET /api/v1/games/mazex/config   (обычная пользовательская авторизация)
→ { "ws": "wss://telegram.resager.ru/app/mazex/ws", "ticket": "<одноразовый, 60 с>" }
```

Билет — ровно тот же приём, что у пульта ТВ (`/api/v1/tv/remote/{ticket}`):
вебсокету нельзя передать заголовок авторизации, поэтому ядро выдаёт короткий
одноразовый пропуск, а сервис меняет его на личность через `/session/resolve`.
**BOT_TOKEN игровому сервису не отдаём** — он не проверяет подписи Telegram
сам, этим занимается ядро.

Протокол (JSON-сообщения по вебсокету, черновик):

| Направление | Тип | Поля |
|---|---|---|
| → сервис | `hello` | `ticket`, `variant`, размеры окна в клетках |
| ← клиент | `init` | `seed`, `cols`, `rows`, `shortest`, выбранный стиль стен, рекорд |
| → сервис | `input` | `dir` (вектор джойстика) или `step` (шаг крестиком), `t` |
| ← клиент | `tick` | позиция, посещённые клетки пачкой, таймер |
| ← клиент | `finish` | итог партии, обновлённый рекорд |

Темп: сервер считает шаги по своему времени и шлёт `tick` 10–15 раз в секунду,
клиент между тиками сглаживает движение. Лабиринт клиент строит **сам из
seed** тем же генератором — гонять сетку по сети незачем (у «гигантского» это
40 КБ на партию).

## 7. Локальная разработка

```bash
# 1. ядро
cd habits/backend
GOTOOLCHAIN=auto /usr/local/go/bin/go build -o "$SP/srvtest" ./cmd/server
DATABASE_URL='postgres://postgres:postgres@localhost:5432/streaks?sslmode=disable' \
  DEV_AUTH_BYPASS=true DEV_USER_ID=1 ADMIN_IDS=1 ADDR=:8081 DATA_DIR="$SP/data" \
  "$SP/srvtest" &

# 2. игровой сервис (новый каталог habits/mazex)
CORE_URL=http://127.0.0.1:8081 SERVICE_TOKEN=dev ADDR=:8090 go run ./cmd/mazex &

# 3. фронт
cd habits/frontend/app && npm run dev
```

В дев-режиме ядро принимает `Authorization: tma dev`, а сервису можно
разрешить `SERVICE_TOKEN=dev` без строки в БД — ровно по той же логике, что
`DEV_AUTH_BYPASS`. На проде такой режим должен быть выключен.

Грабли, уже известные по играм:
- `requestAnimationFrame` и таймеры в фоновой вкладке Chrome не вызываются —
  автопроверки движения делать через `MessageChannel`, а время считать суммой
  `dt` в игровом цикле (так сделано в лабиринте);
- `pkill -f` рвёт составные команды (exit 144) — убивать по PID отдельной
  командой.

## 8. Деплой

### 8.1. Контейнер

В `habits/deployment/streaks/docker-compose.yml` добавить сервис рядом с `app`:

```yaml
  mazex:
    build: ./mazex           # Dockerfile сервиса
    restart: unless-stopped
    environment:
      ADDR: :8090
      CORE_URL: http://app:8081          # по имени сервиса внутри стека
      SERVICE_TOKEN: ${MAZEX_TOKEN:?set MAZEX_TOKEN in .env}
    depends_on:
      app:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "wget", "-q", "-O", "/dev/null", "http://127.0.0.1:8090/healthz"]
      interval: 15s
      timeout: 5s
      retries: 5
    networks:
      default: {}
      proxy:
        aliases: [habits-mazex]          # под этим именем его видит Caddy
```

`MAZEX_TOKEN` дописывается в `/opt/habits/.env` руками, один раз, и той же
строкой вставляется в `game_services`. `.env` в репозиторий не попадает.

### 8.2. Caddy

В `habits/deployment/streaks/Caddyfile.habits` (его копирует и перезагружает
`deploy.sh`, на сервере файл править нельзя) в блок `telegram.resager.ru`:

```caddy
	handle_path /app/mazex/* {
		reverse_proxy habits-mazex:8090
	}
```

Вебсокет Caddy проксирует сам, дополнительных директив не нужно.

### 8.3. Скрипт выкладки

`deploy.sh` сейчас собирает бэкенд и фронт и поднимает стек. Добавить:
1. сборку бинарника сервиса (`CGO_ENABLED=0 GOOS=linux GOARCH=amd64`) в
   каталог стейджа;
2. копирование `mazex/` рядом с остальным в `/opt/habits`;
3. в проверках в конце — `curl` по `https://telegram.resager.ru/app/mazex/healthz`.

`docker compose up -d` поднимет новый контейнер сам; остальной стек при этом
не перезапускается, если его образ не менялся.

### 8.4. Порядок релиза (обязателен, из skill)

1. Реализовать → проверить локально (curl + браузер).
2. Версия в `frontend/app/src/shared/version.ts` (minor для фичи).
3. `meta.version` страницы «Игры» в `router/index.ts`.
4. `DOCS.md` + `HelpView.vue`.
5. Миграции: отдельная для таблиц (`mazex_runs`, `game_services`) и отдельная
   для записи релиза в `releases`.
6. `./habits/deployment/streaks/deploy.sh` — все проверки 200.
7. Коммит в `dev_postgres` → `git push origin dev_postgres`.
8. Публичный снапшот одним orphan-коммитом (проверки на секреты и `git diff`
   обязательны).

## 9. Безопасность

- Сервису не дают ни `BOT_TOKEN`, ни `DATABASE_URL`: личность игрока он
  узнаёт у ядра по одноразовому билету, данные пишет через внутренний API.
- Токен сервиса — строка в `game_services` и в `.env` на сервере; в репозитории
  его нет. Та же дисциплина, что у агентов (`~/.config/*.token`).
- Внутренние ручки отвечают 401 на любой запрос без токена сервиса и не
  принимают `user_id` «на слово» в тех местах, где его можно взять из билета.
- Счёт и время считает сервис, клиент их только показывает: иначе рекорд
  ставится правкой переменной в консоли.

## 10. Решения, которые нужны до кода

1. **Что именно «Экстра»?** Варианты: туман войны и фонарик; ключи и двери;
   монеты и очки; гонка вдвоём по одному лабиринту (тот же seed); лабиринт с
   движущимися стенами. От ответа зависит, нужен ли вообще realtime.
2. **Нужен ли второй игрок прямо сейчас.** Если да — в протоколе появляется
   комната, и это ровно тот случай, ради которого затевается сервис. Если
   нет — на первом шаге хватит HTTP, а вебсокет можно отложить.
3. **Темп сервера**: 10–15 тиков в секунду достаточно для лабиринта, но если
   добавится погоня — понадобится 30, и это другой разговор про трафик.
4. **Общая таблица лидеров** между пользователями: по `game_scores` она
   строится, но нужно решить, показывать ли чужие имена (сейчас в играх
   рекорды только свои).
5. **Что делать с незаконченной партией** при перезапуске сервиса: терять
   (просто) или снимать состояние в `mazex_state` (сложнее, но честнее).

## 11. Оценка

| Часть | Оценка |
|---|---|
| Каркас сервиса: HTTP, healthz, конфиг, токен, клиент к ядру | ~3 ч |
| Внутренний API в ядре + миграции + билеты | ~3 ч |
| Вебсокет и протокол (одиночная партия) | ~4 ч |
| Клиентский компонент поверх готового рендера лабиринта | ~4 ч |
| Деплой: compose, Caddy, deploy.sh, проверка на проде | ~2 ч |
| Документация, релиз | ~1,5 ч |

**Итого ~2 дня на одиночную «Экстру» без второго игрока.** Игра вдвоём — плюс
день: комната, синхронизация, уведомление бота о приглашении.
